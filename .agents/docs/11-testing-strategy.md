# 测试策略

## 目标

测试不仅验证页面能用，还必须证明权限、状态、截止、并发、文件校验、隐私和异步任务符合需求。每个缺陷修复先增加能复现问题的测试，再修改实现。

## 测试层级

| 层级 | 工具方向 | 重点 |
| --- | --- | --- |
| 后端单元 | Pytest | Service 状态机、权限、截止、受众、重试与纯函数 |
| 后端集成 | Pytest + 临时 PostgreSQL/MinIO | Repository、约束、事务、预签名、Outbox、迁移 |
| 前端单元 | Vitest + Testing Library | 表单、状态呈现、上传器、无障碍语义 |
| API 契约 | OpenAPI schema + 集成测试 | 请求/响应、错误结构、权限和幂等 |
| 浏览器端到端 | Playwright | 真实注册、邮箱验证直达登录、通知、提交、组队、评语和优秀作业流程 |
| 性能 | k6 或同等工具 | 300 账号基线、100 浏览会话、20 并发分片上传 |
| 安全 | 依赖扫描、静态检查、针对性渗透用例 | XSS、CSRF、会话、越权、对象访问和枚举 |
| 运维验证 | 隔离 Compose 环境 | 健康、备份、恢复、迁移和更新回滚 |

测试依赖必须固定版本并在 CI 中可重复运行。集成测试使用真实 PostgreSQL 和兼容 MinIO，不用 SQLite 替代数据库约束。

## 单元测试重点

- 账号状态机只允许 `pending_email → active ↔ disabled`，最后一个管理员不能被降级或禁用。
- 受众组合的全部、并集、交集和发布快照计算。
- 上海时区展示与 UTC 存储，公共截止和个人延期优先级；覆盖 NFR-005。
- 赛事阶段顺序、报名窗口、人数上下限、队伍锁定和队长转让。
- 提交至少一种内容、版本号递增、2 GiB 合计和附件上下文匹配。
- Markdown 清洗、外链协议、文件名规范化和扩展名白名单。
- Outbox 退避、最大次数、锁租约、幂等键与永久/临时 SMTP 错误分类。

## 集成测试重点

- 所有唯一、检查、外键和部分唯一索引实际生效。
- 并发双注册、双加入队伍、双版本提交和重复发布只有一个成功业务结果。
- 业务写入、审计和 Outbox 在同一事务提交；事务失败不得留下部分数据。
- Session 哈希、过期、撤销和 CSRF 校验使用真实数据库路径。
- multipart 初始化、分片恢复、完成、哈希不匹配、终止和孤立清理。
- 下载授权从真实业务引用反查，不能只凭 `file_id` 或上传人放行。
- Worker 使用 `SKIP LOCKED` 多实例领取不会重复完成任务。

## 前端与无障碍测试

- 每个表单测试必填、服务端字段错误、加载、重复点击和成功跳转。
- 键盘完成注册、邮箱验证后的登录、通知阅读、作业提交、建队、邀请加入、评语和优秀作业查看/标记。
- 弹窗/抽屉焦点锁、Escape、焦点恢复、错误聚焦和 `aria-live`。
- 360 px、768 px、1280 px、1440 px 关键页面截图回归。
- 深色文本对比、可见焦点、状态非纯颜色、上传进度语义。
- `prefers-reduced-motion` 下无非必要动画。

## 性能测试

### 数据集

300 个激活学生、10 个管理员、4 个届次、8 个方向、100 条通知、40 个作业、10 场赛事、100 支历史队伍、每项 1～3 个提交版本。

### 场景

- 100 个并发用户读取工作台、通知、作业和赛事列表。
- 20 个用户各以 4 分片并发上传，混合 100 MiB 和接近 2 GiB 文件。
- Worker 同时处理 300 封通知邮件和阶段推进。
- 管理员筛选 300 人提交状态和审计日志。

验收：按 NFR-003，非上传 API P95 小于 500 ms，错误率低于 1%；上传吞吐受校园网络限制，但 API 不因大文件占满进程内存，Outbox 在 SMTP 正常时 10 分钟内清空。

## 迁移、备份与恢复测试

- 空库升级到最新结构；上一个发布版本携带代表数据升级到最新。
- 迁移后验证枚举、检查、部分唯一索引和外键。
- 生产规模副本上测量锁时间；破坏性变更执行展开/收缩演练。
- 从加密备份恢复 PostgreSQL 与 MinIO，运行引用对账并完成登录、提交、评语和下载冒烟测试。
- 恢复演练记录实际 RPO、RTO 和异常，不使用生产密码执行测试。
- 按 NFR-008 验证 Frontend、Backend、Worker、PostgreSQL 与 MinIO 的存活、就绪和依赖异常状态。

## CI 质量门

合并前必须通过：格式检查、静态类型、单元测试、数据库迁移测试、API 契约测试、前端组件测试、依赖漏洞检查和秘密扫描。涉及认证、权限、上传、状态机或迁移的变更必须运行对应集成测试；发布候选必须运行核心 Playwright 流程和 Compose 冒烟测试。

阶段 1 已落地三类 CI Job：Frontend 执行 ESLint、严格 TypeScript、Vitest、生产构建和 `npm audit`；Backend 在真实 PostgreSQL 17 上执行 Ruff、Mypy、Pytest、`pip-audit` 以及 Alembic 升级/降级/再升级；Compose 冒烟构建完整拓扑，通过 Nginx 验证登录骨架和三类健康端点，并扫描常见明文私钥与平台令牌格式。Playwright、镜像漏洞扫描和完整秘密扫描在对应业务页面或生产加固阶段加入，不能以当前基础扫描替代发布前安全复查。

## 测试数据规则

- 不把真实学生姓名、学号、邮箱、提交或评语复制到开发、CI 和截图。
- 固定种子生成明确的虚构数据，邮箱使用保留测试域名。
- 测试失败日志同样执行秘密脱敏；大文件边界测试使用稀疏或流式生成数据，不把 2 GiB 样本提交仓库。
