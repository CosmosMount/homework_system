# 编码规范

## 通用原则

- 代码以职责清晰和长期维护为目标，只增加当前需求需要的抽象。
- 优先扩展已有模块，禁止为相同能力创建第二套工具、状态模型或 API 客户端。
- 函数承担单一任务；超过约 50 行或同时包含多种职责时应拆分，确有必要需用注释说明原因。
- 注释解释设计意图、约束和取舍，不复述显而易见的语法。
- 不静默捕获异常，不使用空 `catch/except`，不把内部堆栈直接返回用户。
- 外部输入、数据库结果和第三方响应在边界验证；内部类型保持明确。
- 禁止日志记录密码、Cookie、CSRF、一次性令牌、完整邀请码、密钥、飞书 tenant token、第三方原始错误正文、私密评语和文件内容。

## Python 与 FastAPI

- 使用受支持的 Python 3.12 小版本并在镜像中固定。
- Ruff 负责 lint/格式，Pyright 或 mypy 严格检查，Pytest 负责测试。
- 所有公共函数、Service、Repository 和 schema 显式标注类型；不得用无约束 `Any` 绕过检查。
- Router 只做协议解析、依赖注入和响应映射；业务规则放 Service，SQL 放 Repository。
- Service 方法命名使用业务动作，如 `publish_announcement`、`join_team`，不用含糊的 `handle`、`process`。
- 数据库事务由 Service 明确控制；Repository 不自行提交事务。
- Pydantic 输入、输出和 ORM 模型分离，禁止把 ORM 对象直接序列化为公共 API。
- 时间只使用带时区 `datetime`，业务代码通过可注入时钟取得当前时间。
- 异常使用稳定的领域错误类型和错误码；Router 统一映射 HTTP，不在各路由重复拼错误结构。
- 后台 Worker 与 API 复用 Service 和 Repository，不复制业务逻辑。

## TypeScript 与 Next.js

- 开启 TypeScript `strict`，禁止未说明的 `any`、非空断言和无边界类型断言。
- React 组件使用函数组件；Server Component 为默认，只有交互和浏览器 API需要时才添加 `use client`。
- API 响应先由统一 schema 验证，再转换为前端领域类型。
- 不在组件中散落原始 `fetch`、错误码判断和 Cookie 处理；使用按业务域组织的 API Client。
- URL 查询参数是列表筛选和分页的权威状态；局部表单状态不放全局 store。
- 可访问名称、标签、焦点与键盘操作是组件完成条件，不在后期补丁处理。
- 样式使用设计令牌和共享基础组件；禁止在页面随意引入相近但不一致的色值、圆角和间距。
- 不使用 `dangerouslySetInnerHTML` 渲染用户输入；清洗后的 Markdown 只能通过集中封装组件呈现。

## SQL 与迁移

- 表名和字段使用 `snake_case`，约束和索引使用可读名称，如 `uq_team_member_active_competition`。
- 数据完整性优先使用数据库外键、唯一和检查约束，再由 Service 提供友好错误。
- 查询只选择所需字段，列表必须分页；避免 N+1，并用真实查询计划验证关键索引。
- 所有结构变化通过 Alembic；迁移文件不得依赖未部署的应用代码。
- 迁移必须说明前滚、回滚或不可逆原因，并在 PostgreSQL 上测试。
- 不直接编辑已进入共享环境的迁移；新增修复迁移。

## API

- 路径、字段、错误码和权限以 `06-api-specification.md` 为准；变更先更新文档和测试。
- UUID、时间、分页、错误、幂等和 `revision` 规则保持全局一致。
- 不返回数据库内部字段、对象键、哈希、令牌、管理员内部原因和未经选择的私密内容。
- 写操作必须考虑重复请求、并发状态变化和事务失败。
- 资源不可见时按规范返回 404，不能用不同状态泄露存在性。

## 错误和日志

- 用户错误返回稳定错误码和可操作中文信息；内部日志使用结构化字段和请求 ID。
- 日志使用事件名称，不拼接包含用户输入的大段字符串。
- 已预期的业务冲突记录为信息或警告，未预期异常记录堆栈并返回通用 500。
- 外部依赖错误分类为可重试、永久失败或配置错误，不能无限重试。
- 外部 API 客户端必须固定可信协议与主机、拒绝重定向并限制超时、分页和响应大小；不得把外部资源 URL 直接当作服务端下载目标。

## 测试

- 测试名称表达“条件—行为—结果”，每个测试只证明一个主要规则。
- 单元测试不依赖真实时间、随机网络或共享状态；使用可注入时钟和固定种子。
- 数据库规则使用真实 PostgreSQL 集成测试，不用 SQLite 模拟。
- 修复缺陷必须加入回归测试；高风险权限用例覆盖允许与拒绝两侧。
- 测试数据必须虚构，不复制真实学生资料和作品。

## 依赖管理

- 新依赖必须解决明确问题，说明维护状态、许可证、安全和替代方案。
- 前后端锁文件提交仓库，生产镜像按锁文件安装，不使用浮动大版本。
- 能用标准库或现有依赖清晰完成的功能不增加新包。
- 定期检查漏洞；升级导致接口或行为变化时记录 ADR 或变更说明。

## Git 与提交

- 分支默认使用 `codex/` 前缀或团队约定前缀。
- 提交使用 `feat:`、`fix:`、`refactor:`、`docs:`、`test:`、`chore:`。
- 一个提交只包含一个逻辑主题，不混入无关格式化和重构。
- 不提交真实 `.env`、证书、备份、上传样本、生成日志、生产数据或密钥。
- 合并说明列出需求编号、迁移、测试结果、部署影响和已知风险。

## 文档同步

- 产品行为改变：更新 `01-product-requirements.md` 和页面规格。
- 路由/API改变：更新 `02-information-architecture.md`、`06-api-specification.md` 和契约测试。
- 表、枚举或约束改变：更新 `07-database-schema.md`、迁移与迁移测试。
- 安全、上传或部署改变：更新对应专题文档和架构决策。
- 完成工作：更新任务、变更记录和必要的项目记忆。
