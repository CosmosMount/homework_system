# 架构决策记录

所有条目状态均为 `Accepted`。ADR-001～ADR-016 日期为 2026-08-23，ADR-017～ADR-018 日期为 2026-08-24，ADR-019～ADR-022 日期为 2026-08-25，ADR-023～ADR-029 日期为 2026-08-26～27。改变已接受决策必须新增替代 ADR，说明迁移和兼容影响，不能静默改写历史原因。

## ADR-001：单校单组织、非多租户

**决策**：首版只服务一个学校内的一个组织，数据表不增加 `tenant_id`。

**原因**：当前用户、权限和部署边界明确；提前加入租户隔离会扩大所有查询、约束、运维和安全面。

**替代方案**：多租户 SaaS 被拒绝，因为没有已确认的跨校需求。

**后果**：未来多校需求必须单独设计租户迁移，不能仅添加一个字段后宣称隔离完成。

## ADR-002：动态系统与现有官网独立

**决策**：本仓库不修改、不复制、不运行时调用现有战队官网与飞书培训知识库；作业只保存可选外部资料 URL。

**原因**：现有站点是成熟静态内容链路，动态认证、数据库和大文件业务具有不同部署与安全需求。

**替代方案**：把官网迁入全栈项目、在首版增加双向同步，均因耦合和迁移风险被拒绝。

**后果**：首版用户分别访问两个系统；后续导航集成需要新 ADR。

## ADR-003：Next.js + FastAPI 模块化单体

**决策**：前端使用 Next.js App Router，后端使用 FastAPI 模块化单体，按 Router、Service、Repository 分层。

**原因**：Next.js适合现有团队视觉资产，FastAPI 适合明确 API、异步 I/O 和 Python 服务；模块化单体足以支撑当前规模。

**替代方案**：Next.js 全栈会弱化业务与对象存储边界；Django 单体减少前端复用；微服务增加运维复杂度。

**后果**：前后端共享 OpenAPI 契约而不共享运行时代码；不得提前拆微服务。

## ADR-004：服务端 Session，不使用长期浏览器 JWT

**决策**：使用 PostgreSQL 服务端 Session 和 `Secure`、`HttpOnly`、`SameSite=Lax` Cookie。

**原因**：账号禁用、角色变化和密码重置要求立即撤销访问；Session 更易实现集中撤销。

**替代方案**：长期 JWT 因撤销和权限变更延迟被拒绝；浏览器本地存储令牌因 XSS 风险被拒绝。

**后果**：受保护写操作还必须执行 CSRF；数据库短暂不可用时不能创建或验证 Session。

## ADR-005：PostgreSQL 保存关系数据与约束

**决策**：用户、受众、赛事、队伍、提交、Outbox 和审计使用 PostgreSQL，ID 使用 UUIDv7，时间使用 `TIMESTAMPTZ`。

**原因**：领域具有强关系、事务、唯一约束、部分索引和并发锁需求。

**替代方案**：SQLite 并发和运维能力不足；文档数据库无法自然表达一赛一队和提交所有者约束。

**后果**：测试必须使用真实 PostgreSQL；结构变化只通过 Alembic。

## ADR-006：MinIO 私有对象存储与分片直传

**决策**：附件存 MinIO 私有桶，浏览器通过 Nginx 使用短时预签名 multipart URL 直传，默认 16 MiB 分片；每版本合计上限 2 GiB。

**原因**：FastAPI/Next.js 不应中转大文件，MinIO 提供 S3 兼容分片、对象持久化和校验能力。

**替代方案**：数据库 BLOB、应用服务器本地目录和 API 整体上传均因扩展、备份、内存或恢复问题被拒绝。

**后果**：PostgreSQL 与 MinIO 无跨系统事务，必须采用“先验证对象、后绑定版本、孤立对象延迟清理”。

## ADR-007：PostgreSQL Outbox Worker，不引入 Redis

**决策**：邮件、定时发布、赛事阶段和清理任务写入 PostgreSQL `outbox_jobs`，独立 Worker 使用 `FOR UPDATE SKIP LOCKED` 领取。

**原因**：业务数据和任务可以同事务提交，当前规模不需要额外队列服务。

**替代方案**：请求内后台任务可能在重启时丢失；Redis/Celery 增加部署和一致性成本。

**后果**：必须实现幂等键、锁租约、退避、最终失败和积压监控；真实负载不足时不得引入消息队列。

## ADR-008：作业发布时固定受众快照

**决策**：作业发布事务生成逐用户受众快照；学生之后补充或改变可选分类不改变历史作业归属。

**原因**：动态重新计算会让学生突然获得或失去已发布任务，破坏提交统计与追溯。

**替代方案**：每次读取按当前届次/方向计算被拒绝。

**后果**：发布成本与目标人数线性相关，但当前 300 账号规模可接受；修改受众需新建作业而不是改历史快照。

## ADR-009：统一提交聚合，数据库约束个人/团队所有者

**决策**：作业和赛事共用 `submissions`、不可变 `submission_versions`、附件和评语模型；检查约束保证作业对应个人、赛题对应队伍。

**原因**：版本、文件和评语行为一致，重复两套实现会产生漂移；显式外键和检查比无约束多态关系安全。优秀作业只是作业版本上的标记，不改变提交聚合。

**替代方案**：两套提交表会重复核心逻辑；通用 `target_type/target_id` 无法建立外键完整性。

**后果**：Service 仍需验证跨表语义，数据库负责目标/所有者组合和唯一性。

## ADR-010：正式提交版本不可变

**决策**：每次确认提交创建新版本，旧版本不更新、不由学生删除；评语关联具体版本。

**原因**：需要准确追踪截止时内容、管理员反馈对象和优秀作业来源。

**替代方案**：覆盖式文件提交无法解释评语和截止争议。

**后果**：存储量随版本增长，需容量监控和合规删除流程；用户修订必须提交新版本。

## ADR-011：两角色模型

**决策**：首版只设 `student` 和 `admin`，管理员承担用户异常处理、可选分类、发布、批改和赛事管理。

**原因**：当前组织规模和流程不需要助教、评委、出题人等细分权限。

**替代方案**：五角色模型增加授权矩阵和后台复杂度；学生/管理员足以覆盖已确认场景。

**后果**：管理员权限较大，必须加强审计和最后管理员保护；出现真实分工后通过独立权限 ADR 扩展。

## ADR-012：不设计评分和排名

**决策**：作业与赛事只支持私密文字评语，不提供分数、量规、等级、排名、自动评奖或公开评语。

**原因**：系统目标是收集、反馈与展示优秀成果，不是正式教务评分或竞赛计分系统。

**替代方案**：多评委均分、单评委总分和公开榜单均被明确排除。

**后果**：API 和数据库不能保留“以后可能用”的空评分字段；需要时重新开展产品设计。

## ADR-013：优秀作业是作业版本上的上下文标记

**决策**：管理员只能把作业提交版本标记为优秀作业；它只在对应作业中向该作业受众显示原版本文本、链接、附件和作者姓名，私密评语永不展示。赛事提交不能标记。

**原因**：学生在学习具体作业时查看优秀答案最有上下文价值；独立内容域、二次选材和跨赛事来源增加了没有实际用途的页面、状态和数据结构。

**替代方案**：独立范本列表/详情、草稿/发布状态、赛事优秀成果和复制独立文件均被拒绝。

**后果**：`assignment_excellent_submissions` 关联存在期间保护源版本与附件；取消标记后立即从作业隐藏，但源提交与审计保留。

## ADR-014：全业务内容仅登录可见

**决策**：除注册、验证、登录和密码重置外，通知、作业、赛事、提交和作业内优秀作业全部要求登录。

**原因**：平台面向校内组织，包含学生身份、培训安排和作品，不承担公开宣传。

**替代方案**：公开门户与登录工作台的混合模式被拒绝。

**后果**：SEO 不是目标；优秀作业只对对应作业受众展示，不形成全站公开内容。

## ADR-015：首版不内置恶意软件扫描

**决策**：首版执行类型、大小、校验和、权限和不可执行预览控制，但不部署 ClamAV 等自动扫描服务。

**原因**：系统不执行或在线预览文件，校内服务器资源和扫描运维尚未确认；把扫描作为虚假安全承诺风险更高。

**替代方案**：内置扫描服务会增加资源、更新、隔离和误报处理职责。

**后果**：下载文件仍有内容风险，部署和用户提示必须披露；后续引入扫描需定义隔离状态与误报流程。

## ADR-016：指定学校邮箱验证后直接激活

**决策**：公开注册只接受后缀精确为 `hkust-gz.edu.cn` 的邮箱；邮箱验证成功后账号直接从 `pending_email` 进入 `active`，不经过管理员审批，不要求先分配届次、方向或其他组别。

**原因**：学校邮箱已经提供首版所需的成员边界，逐人审批和强制初始分组会增加新生首次登录阻力，并阻塞全体通知与作业使用。

**替代方案**：管理员批准后激活、批准时强制分组和允许配置多个邮箱域名均被拒绝。

**后果**：任何能验证该邮箱域名地址的人都可进入系统，管理员通过事后禁用处理异常账号；届次/方向保持可空，只用于管理员后续定向投放，未分类用户只接收全体内容。

## ADR-017：生产 Secure Cookie 与本地 HTTP 开发隔离

**决策**：生产环境固定使用 `__Host-pnx_session`、`__Host-pnx_csrf` 和 `Secure`；本地 HTTP 开发环境使用无 `__Host-` 前缀的 `pnx_session`、`pnx_csrf`，且生产配置若关闭 Secure 必须启动失败。

**原因**：`__Host-` 前缀按浏览器规范必须同时设置 `Secure`，无法在阶段开发所需的局域网 HTTP 地址工作；若为了本地预览永久取消 Secure，又会削弱生产 Session 边界。

**替代方案**：本地强制自签 HTTPS 会增加所有开发终端的证书信任成本；在 HTTP 上伪造 `__Host-` Cookie 会被现代浏览器拒绝；全环境使用普通 Cookie 名称会降低生产安全基线。

**后果**：Cookie 名称是环境相关配置，前端只通过同源 API 使用而不得硬编码 Session 名；生产验收必须证明 Secure、HttpOnly、SameSite、Path 和无 Domain 属性完整生效。

## ADR-018：Outbox 投递秘密使用独立密钥认证加密

**决策**：邮箱验证与密码重置明文令牌只在创建事务内短暂存在；`one_time_tokens` 仅保存 SHA-256 哈希，Outbox 使用独立 `OUTBOX_ENCRYPTION_KEY` 认证加密投递所需秘密。Worker 领取后在内存中解密并构造邮件，日志、管理 API 和普通查询均不返回明文或密文载荷。

**原因**：认证邮件必须通过可靠 Outbox 异步发送，但随机一次性令牌无法从数据库哈希反推；直接把明文令牌或完整链接写入 JSONB 会让数据库读权限等同于账号接管权限。

**替代方案**：请求内同步发信会在 SMTP 故障时丢失或回滚业务；保存可逆明文、记录令牌日志或提供开发令牌接口均违反安全要求；仅引用令牌行无法恢复邮件所需随机值。

**后果**：部署必须独立生成、保管和轮换 Outbox 加密密钥；存在待投递认证邮件时不能直接丢弃旧密钥。后续实现无中断轮换前，轮换必须先清空或安全重建待处理认证邮件任务。

## ADR-019：MinIO 每日累计增量基于当前周完整备份

**决策**：每周生成包含全部对象与完整清单的加密基线；每天生成相对当前周基线的累计增量，只携带新增/变化对象、删除集合和当日完整对象清单。每个每日备份通过基线备份 ID 和清单 SHA-256 绑定唯一周基线，恢复时先导入周基线，再应用目标日增量。

**原因**：每日归档必须避免重复传输全部 MinIO 内容，同时任一保留中的每日备份应只依赖一个周基线，不能因为删除较早的每日备份而断链。累计增量在当前单校规模下兼顾传输量、恢复步骤和保留安全。

**替代方案**：每日完整复制不满足 NFR-007 的增量要求；逐日以上一天为父节点的增量链会让单日恢复依赖多个归档，并要求保留策略额外保留链上所有已过期日备份，因此被拒绝。

**后果**：宿主机必须维护与备份输出分离、权限为 `0700` 的本地周基线清单状态；缺少有效状态、周归档、校验和或元数据时每日备份必须失败。保留脚本不得删除仍被保留每日备份引用的周基线；隔离恢复必须验证基线清单哈希、应用删除集合并完成数据库/MinIO 全量只读对账。

## ADR-020：Connect 邮箱与空系统首次管理员引导

**替代范围**：替代 ADR-016 中公开注册邮箱域名的当前取值，并替代首次部署依赖交互式管理员命令的做法；ADR-016 的“邮箱验证后直接激活、不经审批、不强制分组”仍有效。

**决策**：新的公开注册及管理员邮箱修改只接受规范化后后缀精确为 `connect.hkust-gz.edu.cn` 的邮箱。空系统首个成功消费邮箱验证令牌、且事务内确认此前不存在任何 `active` 用户的账号成为 `active admin`；后续验证账号成为 `active student`。首次管理员判定使用固定 PostgreSQL 事务级 advisory lock 串行化，并在同一事务写入授予审计。系统仍只有 `student` 与 `admin` 两个角色，“超级管理员”是受最后管理员保护的首个管理员，而不是第三个角色。

**原因**：Connect 地址是当前实际学生身份边界；由首个完成验证的真实账号接管空系统，可取消正常部署对离线 CLI 的依赖，同时邮箱所有权验证、后台角色配置、服务端鉴权、审计与最后管理员保护都能沿用。以“首个完成验证”而非“首个提交注册”判定，可避免未验证账号占用管理员席位。

**替代方案**：新增 `super_admin` 角色会扩大权限矩阵并重复最后管理员能力；按最早注册时间授予会被未验证账号抢占；无锁统计会在并发验证时产生多个初始管理员；继续要求 CLI 创建首个管理员会让正常首次部署依赖容器内人工凭据操作，因此均被拒绝。

**后果**：数据库约束允许旧 `@hkust-gz.edu.cn` 存量账号与新 Connect 账号共存，但应用层所有新邮箱写入只接受 Connect，不自动猜测或改写身份地址。已有任意 `active` 用户的升级库不会自动授予新管理员；若历史库没有管理员，必须使用已有受控恢复命令并记录操作。迁移产生 Connect 数据后不能盲目降级到旧约束，应采用前滚修复或先执行经批准的身份处置。

## ADR-021：Connect 邮箱前缀作为派生登录用户名

**决策**：不新增用户名列。Connect 邮箱规范化后的 local-part 自动作为用户名；登录标识不含 `@` 时补全当前 Connect 域名，包含 `@` 时按完整邮箱规范化。旧域名存量账号只支持完整邮箱。登录 API 使用 `identifier`，临时兼容旧 `email` 请求字段；认证 Service 规范化后才查询、限流和记录安全事件。

**原因**：用户名与学校身份邮箱天然一一对应，派生可避免另一套名称的编辑、漂移和唯一约束；把两种输入合并为同一规范化邮箱可防止切换登录形式绕过限流。保留完整邮箱路径可继续服务旧域名存量账号。

**替代方案**：独立用户名列会引入迁移、冲突处理和账号恢复语义；让旧域名也使用前缀会与同前缀 Connect 账号产生歧义；仅在前端补域名无法约束 API 客户端或统一限流，因此均不采用。

**后果**：用户名随 Connect 邮箱修改而自然变化，没有单独改名接口；用户名登录仍执行密码、`active` 状态、邮箱验证和统一错误检查。注册后的验证邮件能否实际送达仍取决于部署方提供可用校园 SMTP，不能通过用户名功能绕过验证。

## ADR-022：唯一已验证账号必须持久化为管理员

**替代范围**：替代 ADR-020 中“已有任意 `active` 用户的升级库不会自动授予新管理员、无管理员历史库只能走 CLI 恢复”的绝对规则。多账号且无管理员的异常历史库仍必须走受控恢复。

**决策**：当 `users` 表恰好只有一行，且该账号处于 `active`、已经完成邮箱验证、角色仍为 `student` 时，系统必须把它持久化为 `admin`。登录事务在密码和账号状态校验成功后获取与首次管理员相同的固定 PostgreSQL advisory lock，确认不存在其他账号，再提升角色、增加 revision、撤销旧 Session、写入 `user.single_account_admin_granted` 审计并创建新的管理员 Session。发布迁移对符合相同条件的历史唯一账号执行一次数据修正，使已有 Session 的下一次请求也能读取真实管理员角色。迁移降级不自动撤销已经授予的管理员角色。

**原因**：单账号部署如果只有一个已验证 student，会失去全部后台入口；仅在前端或单个依赖中“视为管理员”会造成响应角色、Session 生命周期、审计和后端授权不一致。把角色持久化并复用事务锁可以同时修复历史数据、保持两角色模型，并避免并发注册/登录产生错误提升。

**替代方案**：前端隐藏式兜底和只在 `require_admin` 中临时放行都会绕过真实角色与审计；每次受保护请求统计用户数会给所有学生请求增加数据库开销；启动时无条件修正会把部署启动与业务数据写入耦合；继续只依赖 CLI 不能满足单账号系统自动可管理的产品要求，因此均不采用。

**后果**：`pending_email`、`disabled` 或多账号数据库不会自动提升；“只有一个账号”按用户表全部账号计算，不把禁用账号视为已删除。登录提升会使旧 Session 失效并使用管理员 4 小时空闲期限。数据迁移只更新角色与审计，不改变数据库结构；回滚应用镜像时保留 admin 可避免重新造成无人管理，后续角色调整必须通过受审计的管理员接口。
## ADR-023：校内赛只提供公告与组队

**决策**：新赛事只用于发布校内赛公告、开放报名和完成队伍组建；不创建赛题、赛事作品版本或赛事评语。现有赛题表和 API 保留为历史数据兼容路径，前端不再提供创建、编辑、浏览或提交入口。

**原因**：当前校内赛的实际需求是统一公告和组队，赛题与作品提交会引入不需要的截止、附件、队长提交和评语流程，增加管理和使用成本。

**替代方案**：继续要求至少一个赛题才能发布、删除历史赛题表，或为公告赛事新增一套独立状态机，都会破坏已有数据或重复实现，因此不采用。

**后果**：赛事时间字段中的 submission_start 和 submission_end 在新流程中分别作为组队锁定时间和赛事结束时间使用；数据库结构不变，不做迁移删除。历史赛事接口继续按原授权规则提供，但不属于新产品流程。


## ADR-024：管理员当前 Session 的临时学生视图

**决策**：管理员可以在当前 Session 开启或关闭学生视图。Session 增加 `student_view` 标记，`AuthenticatedContext` 同时计算真实角色和有效角色；学生视图只把有效角色降为 `student`，不修改 `users.role`。所有管理员 API 必须要求真实 `admin` 且未开启学生视图，学生业务按有效角色鉴权。

**原因**：管理员需要验证学生端工作台、通知、作业、赛事和提交体验，但不能通过前端隐藏形成权限边界；把状态放在可撤销 Session 中能支持同会话返回并保留真实角色。

**替代方案**：新增第三种 `student_view` 用户角色会污染角色模型；只在前端切换导航无法阻止直接调用管理员 API；复制登录 Session 会增加令牌和撤销竞态，因此均不采用。

**后果**：切换开启/关闭写审计；管理员学生视图不能访问管理接口或编辑管理员资料。其他管理员将该账号真实角色改为 `student` 时，角色事务撤销全部 Session，原按钮随 Session 失效，本人必须以学生身份重新登录，不能自助恢复管理员。`20260826_0008` 仅增加可回滚的 `sessions.student_view` 列。

**补充**：学生业务读取保留固定快照语义；仅管理员学生视图在服务端按当前作业受众配置做临时预览，以便唯一管理员账号也能检查“全部学生”作业。该预览不创建受众、通知、邮件或统计记录，且提交、上传和优秀作业读取共用同一临时授权。


## ADR-025：移除届次产品设置

**决策**：产品界面不再提供届次创建、启停、用户分配或通知/作业新建受众选择；当前可维护分类收敛为技术方向。旧 `/admin/cohorts` API、`cohorts` 表、用户 `cohort_id` 及历史通知/作业关联保留为兼容路径，编辑历史资源时原样保留届次受众，不新增破坏性迁移。

**原因**：当前校内培训只需要按技术方向或全体学生投放，继续暴露届次设置会增加管理成本和误操作风险。直接删除表和关联会破坏历史通知、作业快照及审计追溯。

**后果**：新前端请求始终发送空 `cohort_ids`；未设置方向的学生仍可正常登录并接收全体内容。若未来彻底移除数据结构，必须另行提供备份、数据清理、迁移前滚和回滚方案。


## ADR-026：单一当前校内赛管理入口

**决策**：管理员入口将赛事管理命名为“校内赛”，列表页只展示当前未归档赛事及其队伍，不提供多赛事创建按钮。首次配置仍保留兼容路由；服务层在创建前检查未归档赛事，已有当前赛事时返回稳定的 `409 CAMPUS_COMPETITION_EXISTS`。已归档赛事和历史赛题接口继续保留为只读/兼容数据。

**原因**：本组织实际只有一条校内赛公告、报名和组队流程，多赛事导航会制造不必要的配置分支；将队伍作为管理首页主内容更符合管理员工作流。

**替代方案**：删除历史赛事数据、物理删除创建 API 或为单赛事新增独立数据库表都会破坏兼容性或重复领域模型，因此不采用。

**后果**：若历史库已有多条未归档赛事，管理页选择最新一条并保留旧记录可读；部署方应通过受控管理员操作归档异常旧赛事。该规则不新增数据库字段或迁移。


## ADR-027：学生校内赛入口直接作为队伍中心并支持主动自动分配

**决策**：学生 `/competitions` 只展示当前未归档校内赛公告、本人报名/队伍状态和公开队伍目录。目录按名称搜索和分页，仅返回队伍名称、状态及人数。已报名且无队伍学生可以主动申请自动分配；事务锁定赛事和所有候选 `forming` 队伍，优先加入人数较少的未满队伍，无候选时自动建队并只返回一次邀请码，一赛一队部分唯一索引处理并发冲突。

**原因**：单一校内赛约束下，多赛事列表增加无效导航；学生真正需要的是找到可加入队伍或在没有社交匹配时获得明确去向。主动申请避免系统未经本人确认改变队伍，人数最少优先可以逐步平衡成形队伍。

**替代方案**：继续展示历史/多赛事列表、公开成员名单供学生联系、由 Worker 全量随机分队和只允许管理员手工分配，分别会增加产品分支、泄露身份、缺少本人确认或增加管理负担，因此不采用。

**后果**：目录不能包含成员姓名、学号或邀请码；自动分配必须仅在报名期、已报名且无队伍时执行，并对满队、重复入队和锁队返回稳定错误。无候选时申请人成为自动队伍队长，需要保存一次性邀请码或后续主动轮换。


## ADR-028：独立登录态意向调查与本地二维码

**决策**：新增独立 `intentions` 领域，管理员创建单选/多选调查并按 `draft → open → closed → archived` 推进；学生只维护本人一份当前回答，管理员只读取匿名人数/比例汇总。管理员可轮换二维码 token，数据库仅保存 SHA-256；二维码由前端本地生成，扫码仍要求 Session 登录并通过安全同源 `next` 返回原调查。

**原因**：培训方向和组队岗位意向需要在移动端快速填写、允许关闭前修改，同时不能把个人选择公开给其他学生或第三方二维码服务。独立领域比把动态问卷塞入通知或用户固定字段更能表达状态、选项和重复填写规则。

**替代方案**：使用匿名公开二维码、第三方表单/二维码服务、把答案写入用户方向字段或把每次修改保留为公开历史，都会削弱身份校验、数据边界、隐私或业务语义，因此不采用。

**后果**：新增可回滚 `20260827_0009` 四表迁移；同一调查/学生由数据库唯一约束保证一份回答。二维码 token 只定位调查且轮换后旧码 404，不能替代登录、CSRF 或开放状态校验；统计不得连接输出姓名、学号、补充说明或单人答案。

## ADR-029：八位密码下限与既有弱密码防护

**决策**：注册、密码重置和管理员命令行创建账号统一接受 8～128 个 Unicode 字符的密码。继续使用 Argon2id，拒绝常见泄露密码以及与邮箱或学号高度相似的值；7 位及以下仍返回稳定的 `PASSWORD_TOO_SHORT`。

**原因**：当前使用者明确希望 8 位密码即可，统一下限可以降低注册和找回密码的输入负担。长度放宽不应绕过密码哈希、最大长度、常见密码或身份相似性防护。

**替代方案**：维持 12 位下限不符合当前产品要求；限定密码恰好 8 位会降低密码管理器和长口令可用性；强制大小写、数字和符号组合会制造可预测模式且增加使用负担，因此均不采用。

**后果**：前后端提示和浏览器约束必须统一为 8 位，服务端仍是最终校验边界；新增常见 8 位密码拒绝项和 7、8、128、129 位回归。不改变现有密码哈希、账号数据、API 结构或数据库，无需迁移。
