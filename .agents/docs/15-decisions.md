# 架构决策记录

除明确标注被替代范围的条目外，所有条目状态均为 `Accepted`。ADR-001～ADR-016 日期为 2026-08-23，ADR-017～ADR-018 日期为 2026-08-24，ADR-019～ADR-022 日期为 2026-08-25，ADR-023～ADR-032 日期为 2026-08-26～27，ADR-033～ADR-035 日期为 2026-08-28，ADR-036～ADR-044 日期为 2026-08-29。改变已接受决策必须新增替代 ADR，说明迁移和兼容影响，不能静默改写历史原因。

## ADR-001：单校单组织、非多租户

**决策**：首版只服务一个学校内的一个组织，数据表不增加 `tenant_id`。

**原因**：当前用户、权限和部署边界明确；提前加入租户隔离会扩大所有查询、约束、运维和安全面。

**替代方案**：多租户 SaaS 被拒绝，因为没有已确认的跨校需求。

**后果**：未来多校需求必须单独设计租户迁移，不能仅添加一个字段后宣称隔离完成。

## ADR-002：动态系统与现有官网独立

**状态**：`Partially Superseded by ADR-031`。关于“不复制或同步飞书培训知识库”的绝对限制已被 ADR-031 替代；不修改现有官网、不依赖官网运行时以及不写回飞书的边界继续有效。

**决策**：本仓库不修改、不复制、不运行时调用现有战队官网与飞书培训知识库；作业只保存可选外部资料 URL。

**原因**：现有站点是成熟静态内容链路，动态认证、数据库和大文件业务具有不同部署与安全需求。

**替代方案**：把官网迁入全栈项目、在首版增加双向同步，均因耦合和迁移风险被拒绝。

**后果**：首版用户分别访问两个系统；后续导航集成需要新 ADR。

## ADR-003：Next.js + FastAPI 模块化单体

**决策**：前端使用 Next.js App Router，后端使用 FastAPI 模块化单体，按 Router、Service、Repository 分层。

**原因**：Next.js适合现有团队视觉资产，FastAPI 适合明确 API、异步 I/O 和 Python 服务；模块化单体足以支撑当前规模。

**替代方案**：Next.js 全栈会弱化业务与对象存储边界；Django 单体减少前端复用；微服务增加运维复杂度。

**后果**：前后端共享 OpenAPI 契约而不共享运行时代码；不得提前拆微服务。

## ADR-004：服务端 Session，不使用长期浏览器 JWT

**决策**：使用 PostgreSQL 服务端 Session 和 `Secure`、`HttpOnly`、`SameSite=Lax` Cookie。

**原因**：账号禁用、角色变化和密码重置要求立即撤销访问；Session 更易实现集中撤销。

**替代方案**：长期 JWT 因撤销和权限变更延迟被拒绝；浏览器本地存储令牌因 XSS 风险被拒绝。

**后果**：受保护写操作还必须执行 CSRF；数据库短暂不可用时不能创建或验证 Session。

## ADR-005：PostgreSQL 保存关系数据与约束

**决策**：用户、受众、赛事、队伍、提交、Outbox 和审计使用 PostgreSQL，ID 使用 UUIDv7，时间使用 `TIMESTAMPTZ`。

**原因**：领域具有强关系、事务、唯一约束、部分索引和并发锁需求。

**替代方案**：SQLite 并发和运维能力不足；文档数据库无法自然表达一赛一队和提交所有者约束。

**后果**：测试必须使用真实 PostgreSQL；结构变化只通过 Alembic。

## ADR-006：MinIO 私有对象存储与分片直传

**决策**：附件存 MinIO 私有桶，浏览器通过 Nginx 使用短时预签名 multipart URL 直传，默认 16 MiB 分片；每版本合计上限 2 GiB。

**原因**：FastAPI/Next.js 不应中转大文件，MinIO 提供 S3 兼容分片、对象持久化和校验能力。

**替代方案**：数据库 BLOB、应用服务器本地目录和 API 整体上传均因扩展、备份、内存或恢复问题被拒绝。

**后果**：PostgreSQL 与 MinIO 无跨系统事务，必须采用“先验证对象、后绑定版本、孤立对象延迟清理”。

## ADR-007：PostgreSQL Outbox Worker，不引入 Redis

**决策**：邮件、定时发布、赛事阶段和清理任务写入 PostgreSQL `outbox_jobs`，独立 Worker 使用 `FOR UPDATE SKIP LOCKED` 领取。

**原因**：业务数据和任务可以同事务提交，当前规模不需要额外队列服务。

**替代方案**：请求内后台任务可能在重启时丢失；Redis/Celery 增加部署和一致性成本。

**后果**：必须实现幂等键、锁租约、退避、最终失败和积压监控；真实负载不足时不得引入消息队列。

## ADR-008：作业发布时固定受众快照

**决策**：作业发布事务生成逐用户受众快照；学生之后补充或改变可选分类不改变历史作业归属。

**原因**：动态重新计算会让学生突然获得或失去已发布任务，破坏提交统计与追溯。

**替代方案**：每次读取按当前届次/方向计算被拒绝。

**后果**：发布成本与目标人数线性相关，但当前 300 账号规模可接受；修改受众需新建作业而不是改历史快照。

## ADR-009：统一提交聚合，数据库约束个人/团队所有者

**决策**：作业和赛事共用 `submissions`、不可变 `submission_versions`、附件和评语模型；检查约束保证作业对应个人、赛题对应队伍。

**原因**：版本、文件和评语行为一致，重复两套实现会产生漂移；显式外键和检查比无约束多态关系安全。优秀作业只是作业版本上的标记，不改变提交聚合。

**替代方案**：两套提交表会重复核心逻辑；通用 `target_type/target_id` 无法建立外键完整性。

**后果**：Service 仍需验证跨表语义，数据库负责目标/所有者组合和唯一性。

## ADR-010：正式提交版本不可变

**决策**：每次确认提交创建新版本，旧版本不更新、不由学生删除；评语关联具体版本。

**原因**：需要准确追踪截止时内容、管理员反馈对象和优秀作业来源。

**替代方案**：覆盖式文件提交无法解释评语和截止争议。

**后果**：存储量随版本增长，需容量监控和合规删除流程；用户修订必须提交新版本。

## ADR-011：两角色模型

**决策**：首版只设 `student` 和 `admin`，管理员承担用户异常处理、可选分类、发布、批改和赛事管理。

**原因**：当前组织规模和流程不需要助教、评委、出题人等细分权限。

**替代方案**：五角色模型增加授权矩阵和后台复杂度；学生/管理员足以覆盖已确认场景。

**后果**：管理员权限较大，必须加强审计和最后管理员保护；出现真实分工后通过独立权限 ADR 扩展。

## ADR-012：不设计评分和排名

**决策**：作业与赛事只支持私密文字评语，不提供分数、量规、等级、排名、自动评奖或公开评语。

**原因**：系统目标是收集、反馈与展示优秀成果，不是正式教务评分或竞赛计分系统。

**替代方案**：多评委均分、单评委总分和公开榜单均被明确排除。

**后果**：API 和数据库不能保留“以后可能用”的空评分字段；需要时重新开展产品设计。

## ADR-013：优秀作业是作业版本上的上下文标记

**决策**：管理员只能把作业提交版本标记为优秀作业；它只在对应作业中向该作业受众显示原版本文本、链接、附件和作者姓名，私密评语永不展示。赛事提交不能标记。

**原因**：学生在学习具体作业时查看优秀答案最有上下文价值；独立内容域、二次选材和跨赛事来源增加了没有实际用途的页面、状态和数据结构。

**替代方案**：独立范本列表/详情、草稿/发布状态、赛事优秀成果和复制独立文件均被拒绝。

**后果**：`assignment_excellent_submissions` 关联存在期间保护源版本与附件；取消标记后立即从作业隐藏，但源提交与审计保留。

## ADR-014：全业务内容仅登录可见

**决策**：除注册、验证、登录和密码重置外，通知、作业、赛事、提交和作业内优秀作业全部要求登录。

**原因**：平台面向校内组织，包含学生身份、培训安排和作品，不承担公开宣传。

**替代方案**：公开门户与登录工作台的混合模式被拒绝。

**后果**：SEO 不是目标；优秀作业只对对应作业受众展示，不形成全站公开内容。

## ADR-015：首版不内置恶意软件扫描

**决策**：首版执行类型、大小、校验和、权限和不可执行预览控制，但不部署 ClamAV 等自动扫描服务。

**原因**：系统不执行或在线预览文件，校内服务器资源和扫描运维尚未确认；把扫描作为虚假安全承诺风险更高。

**替代方案**：内置扫描服务会增加资源、更新、隔离和误报处理职责。

**后果**：下载文件仍有内容风险，部署和用户提示必须披露；后续引入扫描需定义隔离状态与误报流程。

## ADR-016：指定学校邮箱验证后直接激活

**决策**：公开注册只接受后缀精确为 `hkust-gz.edu.cn` 的邮箱；邮箱验证成功后账号直接从 `pending_email` 进入 `active`，不经过管理员审批，不要求先分配届次、方向或其他组别。

**原因**：学校邮箱已经提供首版所需的成员边界，逐人审批和强制初始分组会增加新生首次登录阻力，并阻塞全体通知与作业使用。

**替代方案**：管理员批准后激活、批准时强制分组和允许配置多个邮箱域名均被拒绝。

**后果**：任何能验证该邮箱域名地址的人都可进入系统，管理员通过事后禁用处理异常账号；届次/方向保持可空，只用于管理员后续定向投放，未分类用户只接收全体内容。

## ADR-017：生产 Secure Cookie 与本地 HTTP 开发隔离

**决策**：生产环境固定使用 `__Host-pnx_session`、`__Host-pnx_csrf` 和 `Secure`；本地 HTTP 开发环境使用无 `__Host-` 前缀的 `pnx_session`、`pnx_csrf`，且生产配置若关闭 Secure 必须启动失败。

**原因**：`__Host-` 前缀按浏览器规范必须同时设置 `Secure`，无法在阶段开发所需的局域网 HTTP 地址工作；若为了本地预览永久取消 Secure，又会削弱生产 Session 边界。

**替代方案**：本地强制自签 HTTPS 会增加所有开发终端的证书信任成本；在 HTTP 上伪造 `__Host-` Cookie 会被现代浏览器拒绝；全环境使用普通 Cookie 名称会降低生产安全基线。

**后果**：Cookie 名称是环境相关配置，前端只通过同源 API 使用而不得硬编码 Session 名；生产验收必须证明 Secure、HttpOnly、SameSite、Path 和无 Domain 属性完整生效。

## ADR-018：Outbox 投递秘密使用独立密钥认证加密

**决策**：邮箱验证与密码重置明文令牌只在创建事务内短暂存在；`one_time_tokens` 仅保存 SHA-256 哈希，Outbox 使用独立 `OUTBOX_ENCRYPTION_KEY` 认证加密投递所需秘密。Worker 领取后在内存中解密并构造邮件，日志、管理 API 和普通查询均不返回明文或密文载荷。

**原因**：认证邮件必须通过可靠 Outbox 异步发送，但随机一次性令牌无法从数据库哈希反推；直接把明文令牌或完整链接写入 JSONB 会让数据库读权限等同于账号接管权限。

**替代方案**：请求内同步发信会在 SMTP 故障时丢失或回滚业务；保存可逆明文、记录令牌日志或提供开发令牌接口均违反安全要求；仅引用令牌行无法恢复邮件所需随机值。

**后果**：部署必须独立生成、保管和轮换 Outbox 加密密钥；存在待投递认证邮件时不能直接丢弃旧密钥。后续实现无中断轮换前，轮换必须先清空或安全重建待处理认证邮件任务。

## ADR-019：MinIO 每日累计增量基于当前周完整备份

**决策**：每周生成包含全部对象与完整清单的加密基线；每天生成相对当前周基线的累计增量，只携带新增/变化对象、删除集合和当日完整对象清单。每个每日备份通过基线备份 ID 和清单 SHA-256 绑定唯一周基线，恢复时先导入周基线，再应用目标日增量。

**原因**：每日归档必须避免重复传输全部 MinIO 内容，同时任一保留中的每日备份应只依赖一个周基线，不能因为删除较早的每日备份而断链。累计增量在当前单校规模下兼顾传输量、恢复步骤和保留安全。

**替代方案**：每日完整复制不满足 NFR-007 的增量要求；逐日以上一天为父节点的增量链会让单日恢复依赖多个归档，并要求保留策略额外保留链上所有已过期日备份，因此被拒绝。

**后果**：宿主机必须维护与备份输出分离、权限为 `0700` 的本地周基线清单状态；缺少有效状态、周归档、校验和或元数据时每日备份必须失败。保留脚本不得删除仍被保留每日备份引用的周基线；隔离恢复必须验证基线清单哈希、应用删除集合并完成数据库/MinIO 全量只读对账。

## ADR-020：Connect 邮箱与空系统首次管理员引导

**替代范围**：替代 ADR-016 中公开注册邮箱域名的当前取值，并替代首次部署依赖交互式管理员命令的做法；ADR-016 的“邮箱验证后直接激活、不经审批、不强制分组”仍有效。

**决策**：新的公开注册及管理员邮箱修改只接受规范化后后缀精确为 `connect.hkust-gz.edu.cn` 的邮箱。空系统首个成功消费邮箱验证令牌、且事务内确认此前不存在任何 `active` 用户的账号成为 `active admin`；后续验证账号成为 `active student`。首次管理员判定使用固定 PostgreSQL 事务级 advisory lock 串行化，并在同一事务写入授予审计。系统仍只有 `student` 与 `admin` 两个角色，“超级管理员”是受最后管理员保护的首个管理员，而不是第三个角色。

**原因**：Connect 地址是当前实际学生身份边界；由首个完成验证的真实账号接管空系统，可取消正常部署对离线 CLI 的依赖，同时邮箱所有权验证、后台角色配置、服务端鉴权、审计与最后管理员保护都能沿用。以“首个完成验证”而非“首个提交注册”判定，可避免未验证账号占用管理员席位。

**替代方案**：新增 `super_admin` 角色会扩大权限矩阵并重复最后管理员能力；按最早注册时间授予会被未验证账号抢占；无锁统计会在并发验证时产生多个初始管理员；继续要求 CLI 创建首个管理员会让正常首次部署依赖容器内人工凭据操作，因此均被拒绝。

**后果**：数据库约束允许旧 `@hkust-gz.edu.cn` 存量账号与新 Connect 账号共存，但应用层所有新邮箱写入只接受 Connect，不自动猜测或改写身份地址。并发注册最终命中邮箱或学号唯一约束时，认证 Service 必须回滚并按受信任约束名返回既有字段级 400，不解析数据库错误文本，也不把稳定冲突误报为服务端异常。已有任意 `active` 用户的升级库不会自动授予新管理员；若历史库没有管理员，必须使用已有受控恢复命令并记录操作。迁移产生 Connect 数据后不能盲目降级到旧约束，应采用前滚修复或先执行经批准的身份处置。

## ADR-021：Connect 邮箱前缀作为派生登录用户名

**决策**：不新增用户名列。Connect 邮箱规范化后的 local-part 自动作为用户名；登录标识不含 `@` 时补全当前 Connect 域名，包含 `@` 时按完整邮箱规范化。旧域名存量账号只支持完整邮箱。登录 API 使用 `identifier`，临时兼容旧 `email` 请求字段；认证 Service 规范化后才查询、限流和记录安全事件。

**原因**：用户名与学校身份邮箱天然一一对应，派生可避免另一套名称的编辑、漂移和唯一约束；把两种输入合并为同一规范化邮箱可防止切换登录形式绕过限流。保留完整邮箱路径可继续服务旧域名存量账号。

**替代方案**：独立用户名列会引入迁移、冲突处理和账号恢复语义；让旧域名也使用前缀会与同前缀 Connect 账号产生歧义；仅在前端补域名无法约束 API 客户端或统一限流，因此均不采用。

**后果**：用户名随 Connect 邮箱修改而自然变化，没有单独改名接口；用户名登录仍执行密码、`active` 状态、邮箱验证和统一错误检查。注册后的验证邮件能否实际送达仍取决于部署方提供可用校园 SMTP，不能通过用户名功能绕过验证。

## ADR-022：唯一已验证账号必须持久化为管理员

**替代范围**：替代 ADR-020 中“已有任意 `active` 用户的升级库不会自动授予新管理员、无管理员历史库只能走 CLI 恢复”的绝对规则。多账号且无管理员的异常历史库仍必须走受控恢复。

**决策**：当 `users` 表恰好只有一行，且该账号处于 `active`、已经完成邮箱验证、角色仍为 `student` 时，系统必须把它持久化为 `admin`。登录事务在密码和账号状态校验成功后获取与首次管理员相同的固定 PostgreSQL advisory lock，确认不存在其他账号，再提升角色、增加 revision、撤销旧 Session、写入 `user.single_account_admin_granted` 审计并创建新的管理员 Session。发布迁移对符合相同条件的历史唯一账号执行一次数据修正，使已有 Session 的下一次请求也能读取真实管理员角色。迁移降级不自动撤销已经授予的管理员角色。

**原因**：单账号部署如果只有一个已验证 student，会失去全部后台入口；仅在前端或单个依赖中“视为管理员”会造成响应角色、Session 生命周期、审计和后端授权不一致。把角色持久化并复用事务锁可以同时修复历史数据、保持两角色模型，并避免并发注册/登录产生错误提升。

**替代方案**：前端隐藏式兜底和只在 `require_admin` 中临时放行都会绕过真实角色与审计；每次受保护请求统计用户数会给所有学生请求增加数据库开销；启动时无条件修正会把部署启动与业务数据写入耦合；继续只依赖 CLI 不能满足单账号系统自动可管理的产品要求，因此均不采用。

**后果**：`pending_email`、`disabled` 或多账号数据库不会自动提升；“只有一个账号”按用户表全部账号计算，不把禁用账号视为已删除。登录提升会使旧 Session 失效并使用管理员 4 小时空闲期限。数据迁移只更新角色与审计，不改变数据库结构；回滚应用镜像时保留 admin 可避免重新造成无人管理，后续角色调整必须通过受审计的管理员接口。
## ADR-023：校内赛只提供公告与组队

**决策**：新赛事只用于发布校内赛公告、开放报名和完成队伍组建；不创建赛题、赛事作品版本或赛事评语。现有赛题表和 API 保留为历史数据兼容路径，前端不再提供创建、编辑、浏览或提交入口。

**原因**：当前校内赛的实际需求是统一公告和组队，赛题与作品提交会引入不需要的截止、附件、队长提交和评语流程，增加管理和使用成本。

**替代方案**：继续要求至少一个赛题才能发布、删除历史赛题表，或为公告赛事新增一套独立状态机，都会破坏已有数据或重复实现，因此不采用。

**后果**：赛事时间字段中的 submission_start 和 submission_end 在新流程中分别作为组队锁定时间和赛事结束时间使用；数据库结构不变，不做迁移删除。历史赛事接口继续按原授权规则提供，但不属于新产品流程。


## ADR-024：管理员当前 Session 的临时学生视图

**决策**：管理员可以在当前 Session 开启或关闭学生视图。Session 增加 `student_view` 标记，`AuthenticatedContext` 同时计算真实角色和有效角色；学生视图只把有效角色降为 `student`，不修改 `users.role`。所有管理员 API 必须要求真实 `admin` 且未开启学生视图，学生业务按有效角色鉴权。

**原因**：管理员需要验证学生端工作台、通知、作业、赛事和提交体验，但不能通过前端隐藏形成权限边界；把状态放在可撤销 Session 中能支持同会话返回并保留真实角色。

**替代方案**：新增第三种 `student_view` 用户角色会污染角色模型；只在前端切换导航无法阻止直接调用管理员 API；复制登录 Session 会增加令牌和撤销竞态，因此均不采用。

**后果**：切换开启/关闭写审计；管理员学生视图不能访问管理接口或编辑管理员资料。其他管理员将该账号真实角色改为 `student` 时，角色事务撤销全部 Session，原按钮随 Session 失效，本人必须以学生身份重新登录，不能自助恢复管理员。`20260826_0008` 仅增加可回滚的 `sessions.student_view` 列。

**补充**：学生业务读取保留固定快照语义；仅管理员学生视图在服务端按当前作业受众配置做临时预览，以便唯一管理员账号也能检查“全部学生”作业。该预览不创建受众、通知、邮件或统计记录，且提交、上传和优秀作业读取共用同一临时授权。


## ADR-025：移除届次产品设置

**决策**：产品界面不再提供届次创建、启停、用户分配或通知/作业新建受众选择；当前可维护分类收敛为技术方向。旧 `/admin/cohorts` API、`cohorts` 表、用户 `cohort_id` 及历史通知/作业关联保留为兼容路径，编辑历史资源时原样保留届次受众，不新增破坏性迁移。

**原因**：当前校内培训只需要按技术方向或全体学生投放，继续暴露届次设置会增加管理成本和误操作风险。直接删除表和关联会破坏历史通知、作业快照及审计追溯。

**后果**：新前端请求始终发送空 `cohort_ids`；未设置方向的学生仍可正常登录并接收全体内容。若未来彻底移除数据结构，必须另行提供备份、数据清理、迁移前滚和回滚方案。


## ADR-026：单一当前校内赛管理入口

**决策**：管理员入口将赛事管理命名为“校内赛”，列表页只展示当前未归档赛事及其队伍，不提供多赛事创建按钮。首次配置仍保留兼容路由；服务层在创建前检查未归档赛事，已有当前赛事时返回稳定的 `409 CAMPUS_COMPETITION_EXISTS`。已归档赛事和历史赛题接口继续保留为只读/兼容数据。

**原因**：本组织实际只有一条校内赛公告、报名和组队流程，多赛事导航会制造不必要的配置分支；将队伍作为管理首页主内容更符合管理员工作流。

**替代方案**：删除历史赛事数据、物理删除创建 API 或为单赛事新增独立数据库表都会破坏兼容性或重复领域模型，因此不采用。

**后果**：若历史库已有多条未归档赛事，管理页选择最新一条并保留旧记录可读；部署方应通过受控管理员操作归档异常旧赛事。该规则不新增数据库字段或迁移。


## ADR-027：学生校内赛入口直接作为队伍中心并支持主动自动分配

**决策**：学生 `/competitions` 只展示当前未归档校内赛公告、本人报名/队伍状态和公开队伍目录。目录按名称搜索和分页，仅返回队伍名称、状态及人数。已报名且无队伍学生可以主动申请自动分配；事务锁定赛事和所有候选 `forming` 队伍，优先加入人数较少的未满队伍，无候选时自动建队并只返回一次邀请码，一赛一队部分唯一索引处理并发冲突。

**原因**：单一校内赛约束下，多赛事列表增加无效导航；学生真正需要的是找到可加入队伍或在没有社交匹配时获得明确去向。主动申请避免系统未经本人确认改变队伍，人数最少优先可以逐步平衡成形队伍。

**替代方案**：继续展示历史/多赛事列表、公开成员名单供学生联系、由 Worker 全量随机分队和只允许管理员手工分配，分别会增加产品分支、泄露身份、缺少本人确认或增加管理负担，因此不采用。

**后果**：目录不能包含成员姓名、学号或邀请码；自动分配必须仅在报名期、已报名且无队伍时执行，并对满队、重复入队和锁队返回稳定错误。无候选时申请人成为自动队伍队长，需要保存一次性邀请码或后续主动轮换。


## ADR-028：独立登录态意向调查与本地二维码

**状态**：`Partially Superseded by ADR-035`。独立登录态领域、状态机、本人回答、二维码哈希与安全登录回跳继续有效；单题结构、无限改答和管理员只能查看匿名汇总的部分由 ADR-035 替代。

**决策**：新增独立 `intentions` 领域，管理员创建单选/多选调查并按 `draft → open → closed → archived` 推进；学生只维护本人一份当前回答，管理员只读取匿名人数/比例汇总。管理员可轮换二维码 token，数据库仅保存 SHA-256；二维码由前端本地生成，扫码仍要求 Session 登录并通过安全同源 `next` 返回原调查。

**原因**：培训方向和组队岗位意向需要在移动端快速填写、允许关闭前修改，同时不能把个人选择公开给其他学生或第三方二维码服务。独立领域比把动态问卷塞入通知或用户固定字段更能表达状态、选项和重复填写规则。

**替代方案**：使用匿名公开二维码、第三方表单/二维码服务、把答案写入用户方向字段或把每次修改保留为公开历史，都会削弱身份校验、数据边界、隐私或业务语义，因此不采用。

**后果**：新增可回滚 `20260827_0009` 四表迁移；同一调查/学生由数据库唯一约束保证一份回答。二维码 token 只定位调查且轮换后旧码 404，不能替代登录、CSRF 或开放状态校验；统计不得连接输出姓名、学号、补充说明或单人答案。

## ADR-029：八位密码下限与既有弱密码防护

**决策**：注册、密码重置和管理员命令行创建账号统一接受 8～128 个 Unicode 字符的密码。继续使用 Argon2id，拒绝常见泄露密码以及与邮箱或学号高度相似的值；7 位及以下仍返回稳定的 `PASSWORD_TOO_SHORT`。

**原因**：当前使用者明确希望 8 位密码即可，统一下限可以降低注册和找回密码的输入负担。长度放宽不应绕过密码哈希、最大长度、常见密码或身份相似性防护。

**替代方案**：维持 12 位下限不符合当前产品要求；限定密码恰好 8 位会降低密码管理器和长口令可用性；强制大小写、数字和符号组合会制造可预测模式且增加使用负担，因此均不采用。

**后果**：前后端提示和浏览器约束必须统一为 8 位，服务端仍是最终校验边界；新增常见 8 位密码拒绝项和 7、8、128、129 位回归。不改变现有密码哈希、账号数据、API 结构或数据库，无需迁移。


## ADR-030：新激活学生追加到仍开放的作业快照

**决策**：作业发布事务继续生成初始逐学生受众快照。后续账号完成邮箱验证且最终角色为 `student` 时，在同一激活事务中把仍为 `published`、未过公共截止且按该学生当时分类匹配的作业追加到正式快照；已有行、初始管理员、草稿、关闭、归档、已截止和不匹配作业均跳过。

**原因**：运行库的作业发布时没有普通学生，后续注册学生因此无法查看仍在进行的全体作业，违背新生自主查看和提交作业的核心目标。激活时一次性补录既能让新生加入当前培训，又不会把每次读取改成动态受众。

**替代范围**：补充 ADR-008 的固定快照规则。固定快照仍禁止因学生之后调整方向或管理员编辑作业而重算；本决策只允许在学生首次激活这一明确时点追加当前匹配的开放作业。ADR-024 的管理员学生视图仍只是临时预览，不写入快照。

**替代方案**：让所有学生读取时动态匹配会破坏历史归属和统计；要求管理员复制或重新发布作业会产生重复任务；只手工修复当前学生会让后续注册再次失败，因此均不采用。

**后果**：认证服务在邮箱验证事务内调用作业仓储，API 结构不变且不补发历史邮件。`20260827_0010` 可回滚数据迁移为现有 active student 补录当前开放作业；补录后统计目标人数增加，学生获得正常列表、详情、提交、上传和优秀作业授权。

## ADR-031：以 Worker 同步只读飞书知识库快照

**状态**：`Partially Superseded by ADR-032`。管理员接口、Outbox、常规 Worker、成功快照、PostgreSQL/MinIO 和安全边界继续有效；自定义并发、单篇跳过、仅 Worker 可执行首次初始化及自行设计内容区排布由 ADR-032 替代。

**决策**：允许真实管理员手动创建飞书知识库全量同步 Outbox；只有 Worker 访问固定飞书开放 API，把结构化文档块存入 PostgreSQL、把通过安全校验的媒体存入 MinIO。学生和管理员阅读端只选择最新 `succeeded` 运行，失败运行不切换快照。

**替代范围**：本 ADR 替代 ADR-002 中“本系统不复制、同步飞书培训知识库”的绝对表述；ADR-002 关于不修改现有官网、不依赖官网运行时、不写回飞书和保持动态业务平台边界的部分继续有效。

**原因**：学生需要在同一登录态平台稳定阅读培训资料，管理员需要可控的手动刷新；请求时直连飞书会把外部故障、凭证和延迟带入学生路径，前端抓取会破坏后端授权边界。

**替代方案**：浏览器直连飞书、每次阅读实时代理、复制现有官网运行时、把媒体存 PostgreSQL、同步失败覆盖当前版本均因凭证泄露、SSRF/可用性、耦合或数据边界风险被拒绝。

**后果**：新增五张快照/媒体表、`sync_knowledge` Outbox、Worker 飞书出网和 MinIO 媒体；部署只需 App ID、有效 App Secret 和 Wiki URL，Worker 从 `/wiki/space/{space_id}` 或 `/wiki/{node_token}` 自动解析目标，无三项配置时仍可启动但不能创建新同步。媒体本地化失败按 ADR-032 的精确语义降级；真实租户权限与首次完整同步已于 2026-08-27 验收通过，后续仍由管理员手动触发。

## ADR-032：以指定参考提交约束知识库同步顺序与内容区排布

**状态**：`Partially Superseded by ADR-033`。同步顺序、块转换、媒体失败语义、移动端目录与无顶部文档切换栏继续有效；深色主题、本文目录位于正文左侧以及选文档后保持文档目录展开的页面部分由 ADR-033 替代。

**决策**：以 `HKUSTGZ-ROBOMASTER-PNX/hkustgz-robomaster-pnx.github.io` 提交 `c28f8a0` 作为同步顺序、块转换语义和知识库内容区排布的固定兼容契约。目录使用 50 条分页和串行 DFS 先序遍历，Docx 按目录顺序逐篇执行 blocks 分页再标题读取；图片和附件共用请求前 350 ms 的串行队列，白板发送 PNG Accept。目录、正文或标题失败使整次运行失败；图片/白板失败跳过块，附件失败回退整篇飞书原文。

**页面范围**：登录态 `AppShell` 内的知识库内容区保持参考结构：顶部知识库标题与统计，桌面依次为 280 px 文档目录、位于正文左侧的 180 px 本文目录和正文，移动端使用右下按钮打开包含搜索、文档树和本文目录的全屏目录；不存在顶部文档切换栏。

**替代范围**：替代 ADR-031 中由本项目自行选择正文/媒体并发、跳过受拒目录子树或单篇正文、仅允许常驻 Worker 执行首次初始化，以及自行设计知识库内容区排布的部分。管理员手动接口、常规 Worker、登录鉴权、最后成功快照、PostgreSQL JSONB、MinIO 私有媒体和失败不覆盖旧快照继续有效。

**原因**：首次全量同步长时间运行且自定义降级只生成部分正文，不能满足上线完整性；用户明确指定成熟参考仓库的同步和页面行为为唯一参考，固定提交可以避免上游移动目标导致验收口径漂移。

**保留差异**：不复制参考官网的公开访问、静态 JSON/公开资源目录、硬编码租户域名、公开 token 文件名、宽松链接协议或 GitHub Pages 运行时。部署方仍只需填写 App ID、App Secret 和 Wiki URL；参考仓库的可选 `FEISHU_DOCUMENT_ID` 不成为第四项配置。首次上线内部命令只可接管唯一活动运行，不新增公开 API，后续更新继续由管理员接口交给 Worker。

**后果**：对齐过程不新增数据库迁移；实现和测试覆盖固定顺序、fail-fast、精确媒体失败语义以及桌面/移动排布，只有全部目标 Docx 完成的新运行才能成为当前快照。2026-08-27 的完整运行已以 `succeeded` 发布 228 个目录节点、212 篇文档和 977 个成功媒体引用，13 次允许的资源回退未阻断快照；原 48 篇阶段性快照已被自然替代。


## ADR-033：知识库使用白色阅读主题、右侧本文目录与选文档后收起目录

**状态**：`Partially Superseded by ADR-034`。白色主题、左文档目录、中央正文、右侧本文目录和移动端目录继续有效；“成功打开文档后收起文档目录”由 ADR-034 的“收起系统主要导航并保持文档目录状态”替代。

**决策**：登录态知识库内容区使用白色主题和深色正文。桌面布局从左到右为可折叠 280 px 文档目录、正文、正文右侧可折叠 180 px 本文目录；初次进入时文档目录展开，用户成功打开当前或其他文档后自动收起并保留展开按钮。单篇加载失败不得改变当前文档或文档目录状态。移动端继续使用右下按钮和包含搜索、文档树、本文目录的全屏目录。

**替代范围**：仅替代 ADR-032 的知识库深色主题、本文目录位于正文左侧和选文档后目录展开状态。ADR-032 固定的参考提交同步顺序、块转换、目录/正文/标题 fail-fast、精确媒体降级、无顶部文档切换栏和移动端目录契约继续有效；登录鉴权、成功快照、管理员手动接口、Worker、PostgreSQL/MinIO 与失败不覆盖旧快照均不改变。

**原因**：全平台当前视觉基线是纯白蓝灰主题，右侧本文目录更符合长文阅读时“左侧选文档、中央阅读、右侧页内导航”的信息层次；选中后收起左目录可以把桌面宽度优先留给正文，同时不牺牲重新展开能力。

**后果**：只修改知识库前端组件和组件回归，不涉及公开 API、同步器、数据库迁移或重新同步。测试必须覆盖白色根主题、DOM 顺序、成功后自动收起、失败保留状态以及移动端目录；部署必须隔离并行账号改动，只替换 Frontend。


## ADR-034：打开知识文档时折叠系统主要导航并让本文目录跟随阅读

**状态**：`Accepted`。

**决策**：用户成功打开当前或其他知识文档后，折叠系统最左侧 `AppShell` 主要导航；知识库文档目录保持用户自己的展开/折叠状态。单篇加载失败不得改变主要导航或文档目录状态。正文右侧本文目录使用视口吸附、最大视口高度和内部滚动，并依据页面滚动位置使用 `aria-current="location"` 高亮当前章节。文档目录、搜索框、目录标题栏、目录行和展开/收起按钮复用系统全局设计令牌与控件状态。

**替代范围**：替代 ADR-033 中“成功打开文档后自动收起文档目录”的决策及相应测试后果；ADR-033 的白色主题和三栏顺序继续有效。ADR-032 的同步顺序、块转换、失败语义与移动端目录契约，以及登录鉴权、成功快照、管理员手动接口、Worker 和 PostgreSQL/MinIO 均不改变。

**原因**：用户所称“大导航栏”是跨页面的系统主要导航，阅读时折叠它能释放全局横向空间；文档目录属于阅读器内部信息架构，应保持用户显式控制。右侧本文目录持续跟随并标识当前章节，才能在长文阅读时提供稳定的位置感。统一系统控件样式可避免知识库形成第二套交互语言。

**后果**：共享主导航监听受控的客户端折叠请求，知识库只在成功路径触发；右侧本文目录监听页面滚动且 sticky 祖先不得建立无效滚动容器。回归测试必须同时渲染 `AppShell` 与阅读器，验证成功/失败状态边界、滚动章节高亮和系统样式。本轮不修改 API、同步器、数据库或快照。


## ADR-035：意向调查升级为多题实名问卷并限制提交次数

**状态**：`Accepted`。

**决策**：用户界面把“意向调查”统一升级为“问卷”，每份问卷包含 1～30 道必答单选/多选题，并可设置每人 1～100 次提交上限或不限。每次成功提交覆盖本人最新答案并单调增加累计次数，不保留被覆盖的答案历史。管理员除分题统计外可以读取实名最新答案名单；学生仍只能读取本人答案。既有 `/intentions` 路由、表前缀和模块名作为兼容标识保留。

**替代范围**：替代 ADR-028 的单题 `allow_multiple`、关闭前无限改答和管理员只能查看匿名汇总；ADR-028 的登录态授权、`draft → open → closed → archived` 状态机、本地二维码、token 只存 SHA-256、扫码仍需登录和同源安全回跳继续有效。

**原因**：培训方向需要表达“第一志愿、第二志愿”等多个独立问题，单题选项无法表达题间语义；管理员需要按人安排培训和组队，仅有匿名比例不能完成后续协调。可配置提交次数同时覆盖“一次确认后锁定”和“允许有限修订”两种实际流程。

**替代方案**：把第一/第二志愿编码成选项会丢失题目结构；把每次提交保存为独立公开记录会让管理员难以判断当前意向并扩大个人数据留存；直接改为匿名公共表单会绕过校内账号与授权，因此不采用。

**后果**：新增 `intention_questions`、`max_submissions` 和 `submission_count`，管理员新增受保护的 `/admin/intentions/{survey_id}/responses` 名单接口。提交事务锁定问卷并原子校验次数，审计只记录问卷 UUID 和累计次数，不记录答案。`20260828_0013` 自动把旧调查迁为一个兼容问题，旧回答和选择保留、旧调查默认不限次数；降级会展平多题并丢失题目/次数语义，生产回滚前必须备份。

## ADR-036：反馈答疑采用私密单工单与管理员单答复模型

**状态**：`Accepted`。

**决策**：新增登录态私密反馈答疑域。学生只可创建 `system_feedback` 或 `question` 工单并查看本人记录；真实管理员查看全部工单并填写当前处理结果或答复，首次答复后状态从 `open` 进入 `resolved`，后续按 `revision` 修订同一答复。每次答复在同一事务写工单、脱敏审计和一条站内通知，不发送邮件。

**边界**：反馈答疑不是论坛、即时聊天、客服会话或评价系统，不支持附件、公开列表、评论、多轮消息、点赞、评分、排名、自动回复、学生关闭或重开。正文与答复都使用服务端统一 Markdown 清洗；学生越权读取与不存在统一 404，管理员学生视图按本人学生路径使用且不能进入管理接口。

**原因**：当前业务只需要为校内学生提供可追踪的问题入口和正式管理员答复。单工单单答复能满足处理闭环，并复用现有鉴权、审计和站内通知；引入聊天流、附件和公开互动会扩大隐私、内容治理、存储与并发复杂度，超出当前需求。

**替代方案**：复用作业版本 `feedback` 会混淆提交评语与系统问题的所有权和生命周期；使用公开论坛会暴露学生问题；使用邮件或飞书写回会绕过平台登录态追踪并违反知识库只读边界，因此均不采用。

**后果**：新增 `/help`、`/admin/help` 页面族、六个受保护 API 和 `help_requests` 表。管理员答复使用行锁与 revision 冲突保护，通知事件键包含答复后的 revision；通知和审计不得包含正文。迁移 `20260828_0014` 只建新表，降级会删除全部反馈答疑数据，生产降级前必须备份并优先前滚修复。

## ADR-037：已解答问题采用登录态匿名自动公开

**状态**：`Accepted`。

**决策**：仅 `request_type=question AND status=resolved` 的反馈答疑向所有有效登录用户提供匿名只读列表与详情。公开状态由现有类型和状态派生，不增加字段或人工开关；管理员首次答复问题后自动公开，修订答复直接更新公开内容。公开仓储查询不连接 `users`，响应不含提问者 UUID、姓名、学号、邮箱或 Markdown 源文。

**替代范围**：部分替代 ADR-036 的“全部工单仅本人和管理员可见”及“不支持公开列表”；ADR-036 的单工单单答复模型、本人严格隔离、管理员权限、revision、事务、站内通知、Markdown 清洗和无评论/追问/附件/评分边界继续有效。系统反馈和未解答问题始终私密，匿名互联网访问仍禁止。

**原因**：管理员正式解答后的培训问题通常具有复用价值，登录态匿名展示可以减少重复提问，同时避免暴露学生身份或把内部平台扩展为公开论坛。由状态派生能保证答复事务提交即生效，避免额外字段与工单状态产生不一致。

**替代方案**：由学生或管理员手动勾选公开会产生遗漏、误操作和双状态一致性问题；开放匿名互联网访问会扩大内容与隐私风险；复制问题到独立知识库会形成第二份需同步的内容，因此不采用。

**后果**：新增 `GET /help-requests/public`、`GET /help-requests/public/{request_id}` 和 `/help/public/[requestId]`，原六个操作增为八个。新增查询与响应脱敏回归，不新增数据库迁移；应用回滚只需切回镜像。

## ADR-038：站内提醒徽标按目标业务入口分类

**状态**：`Accepted`。

**决策**：`student_notifications` 继续作为唯一站内提醒记录，但学生侧徽标不再把所有未读集中挂到公告入口。工作台一次返回有效未读总数以及公告、作业、校内赛、反馈答疑四类计数；分类依据既有 `target_type/target_url`，不新增第二套通知表。公告分类只统计仍为 `published` 的目标，归档事务同时把该公告未读提醒标记为已读；公告和本人工单详情通过既有受 CSRF 保护的单条已读接口更新。

**原因**：提醒记录已经包含明确目标，聚合总数挂在“通知”会把答疑解决、作业延期和私密评语误导到公告列表，形成有徽标但列表为空的矛盾。按目标入口分类能直接回答“哪里有新内容”，并保持创建幂等、权限和隐私边界不变。

**替代方案**：新增独立通知中心会重复现有业务入口；仅在前端按标题猜测来源不可靠；删除归档公告提醒会破坏历史记录；通过详情 GET 隐式写已读会违反读取无副作用约定，因此不采用。

**后果**：`GET /dashboard` 保留兼容的 `unread_count` 并新增 `unread_counts`；本人反馈答疑详情只增加当前用户当前工单的未读提醒 ID。侧栏在四个实际入口显示独立徽标，进入公告或本人工单详情后自动发起 POST 已读并刷新。本次无数据库迁移、无新依赖，历史归档公告提醒由查询状态过滤立即失效。

## ADR-039：仅无效登录保留 10 分钟持久失败窗口

**状态**：`Accepted`。

**决策**：登录 Service 在应用层失败计数之前，先按规范化邮箱查询账号并执行真实或 dummy Argon2id 校验。账号为已验证 `active` 且密码正确时直接进入 Session 事务，不读取历史失败事件作为持久等待条件；账号不存在、密码错误、`pending_email` 或 `disabled` 时，继续按规范化邮箱和来源 IP 检查/追加 10 分钟内的 `login_failed` 事件，在邮箱 5 次或 IP 30 次阈值处返回统一 429 和 `Retry-After: 600`。注册、验证邮件重发和密码重置申请继续写安全事件，但不再查询历史计数或返回应用层持久等待。Nginx 的真实来源 IP 瞬时粗限流不变。

**原因**：原流程在账号查询和密码校验前执行 15 分钟失败冷却，使用户完成邮箱验证并改正输入后仍无法证明当前凭据正确，形成“正确密码也只能等待”的恢复死角；注册、重发和重置申请的 1 小时计数也会让正常恢复流程进入长等待。持久失败窗口只用于约束无效登录，且按产品要求收敛为 10 分钟，不能成为已验证用户或恢复入口的持久锁。

**替代方案**：删除 `auth_security_events`、清空特定用户失败记录或重置密码都会修改运行数据；完全取消登录限流会削弱密码防暴力保护；只把全部窗口缩短仍会让正确凭据和恢复入口被历史事件拒绝，因此不采用。

**安全边界**：未知账号继续执行 dummy Argon2id，四类无效状态继续共享错误文案和 10 分钟失败限流；用户名与完整邮箱仍合并到同一规范化邮箱维度。分布式错误登录仍由邮箱/IP 事件和 Nginx 请求桶约束；无持久窗口入口继续记录事件并受 Nginx 瞬时请求桶保护。任何路径都不会删除安全记录或批量重哈希。

**后果**：新增真实 Argon2id、历史失败阈值、10 分钟重试、无持久窗口、状态和规范化标识回归。注册 API 不再声明应用层 `RATE_LIMITED`；API 请求与成功响应、数据库结构、既有安全事件和现有密码哈希均不变，不需要 Alembic 迁移；应用回滚只需恢复旧服务代码。

## ADR-040：未发布内容物理删除、已发布内容归档删除

**状态**：`Accepted`。

**决策**：管理员对通知或作业执行“删除”时，尚未进入学生生命周期的通知 `draft/scheduled` 和作业 `draft` 在行锁事务中物理删除，并取消仍活动的定时发布 Outbox；通知附件只解除绑定，交给既有孤立对象流程延迟清理。已发布通知以及已发布/已关闭作业不物理删除，而是受审计地转为 `archived`；学生列表、详情与作业内优秀作业读取必须排除归档资源，已归档资源重复删除幂等成功。旧归档 API 继续作为兼容路径。

**原因**：管理员的真实目标是纠正误投放并让内容立即退出学生页面，但已发布内容可能关联逐学生提醒、邮件、固定受众、不可变提交版本、私密评语、优秀标记和 MinIO 文件。统一硬删除会破坏 ADR-008、ADR-010、ADR-013 的追溯与不可变约束；只保留原归档读取行为又无法满足从学生端移除的需求。

**替代方案**：为全部内容新增 `deleted_at` 会形成与现有状态重复的全局软删除路径；级联删除已发布作业及提交会破坏正式版本；把“删除”仅做前端过滤会留下可直接访问的后端资源，因此均不采用。

**安全与保留边界**：两个 DELETE 接口只允许真实管理员且要求 CSRF，危险操作由前端二次确认。删除事务写操作者、目标、原状态和 `physical/archive` 模式的脱敏审计；归档通知把未读公告提醒标为已读，但不删除历史提醒或已发送邮件任务。正式提交、评语、优秀标记、已绑定文件元数据和 MinIO 对象保持不变。

**后果**：新增 `DELETE /admin/announcements/{id}` 与 `DELETE /admin/assignments/{id}`，均返回 204；学生对归档通知详情、归档作业列表/详情及其优秀作业读取得到不可见结果。复用现有状态、外键级联和孤立文件 Worker，不新增数据库字段、枚举或 Alembic 迁移。应用回滚若恢复旧学生查询，已归档作业可能重新显示，因此删除功能上线后前后端应作为同一发布单元回滚。

## ADR-041：定向扩展飞书参考契约以保留并渲染公式

**状态**：`Accepted`。

**决策**：同步规范化器把飞书 `block_type=16` 保存为独立 `equation` 块，并把普通富文本元素的 `equation.content` 保存为带 `equation=true` 的 segment，单公式最多保留 20,000 字符。阅读器仅对这些显式结构调用本地 KaTeX，区分行内与独立排版；KaTeX 禁用 trust、限制尺寸和宏展开，把 HTML 扩展作为硬错误，任何解析失败均显示转义后的 LaTeX 源文。

**与既有决策关系**：本 ADR 定向扩展 ADR-032 的块转换契约，修复其固定参考提交 `c28f8a0` 对公式语义的遗漏；ADR-032 的目录 DFS、blocks→标题顺序、媒体队列和失败语义不变，ADR-033～ADR-034 的主题、三栏布局、目录与主导航行为也不变。ADR-031 的登录鉴权、成功快照、Worker、PostgreSQL/MinIO 和失败不覆盖旧快照继续有效。

**原因**：飞书 API 已明确区分富文本公式与独立公式块，但旧同步器把行内公式降为普通字符串并丢弃独立公式，导致培训材料中的反斜杠命令不可读。公式语义必须在同步边界显式保存，不能依赖前端对任意普通文本猜测 `$` 或反斜杠。

**替代方案**：直接显示 LaTeX 源文不能满足公式阅读；按普通文本启发式探测会误判代码和路径；运行时加载 CDN MathJax 会增加外部依赖和内容安全边界；允许 KaTeX trust/HTML 扩展会把飞书文本扩大为 HTML 注入面，因此均不采用。

**后果**：新增锁定的 KaTeX 前端依赖、后端公式规范化和前后端回归。公开 API 路径、数据库表、鉴权、同步触发和 Alembic 均不改变；旧成功快照不会原地改写，部署后需真实管理员手动完成一次新同步，公式结构才进入新的成功快照。应用回滚不会要求数据库降级。

## ADR-042：管理员物理删除反馈答疑并保留脱敏历史

**状态**：`Accepted`。

**决策**：真实管理员可在详情页二次确认后删除任意 `open/resolved`、`system_feedback/question` 工单。Service 先锁定工单，在同一事务把该工单相关未读解决提醒标为已读、写不含标题/正文/答复/学生身份的删除审计，再物理删除 `help_requests` 行；成功返回 204。历史已读提醒和只追加审计保留，学生本人、管理员和公开查询因源行不存在而立即统一不可见。

**与既有决策关系**：定向替代 ADR-036 的“页面不支持删除”边界；ADR-036～ADR-038 的单工单单答复、本人严格隔离、登录态匿名公开、revision、Markdown 清洗、提醒分类和无论坛互动边界继续有效。ADR-040 的未发布/已发布内容分层删除不直接套用：反馈答疑没有正式提交、附件、受众或归档状态，新增软删除会形成第三种状态源。

**原因**：误提、重复或不再适合保留的内部问答需要由管理员从本人记录与匿名公开区同步移除。工单是单一可删除聚合且正文不被其他业务引用，物理删除能用现有查询自然保证所有视图一致；审计与历史已读提醒仍提供不含敏感正文的操作追溯。

**替代方案**：新增 `archived/deleted_at` 会扩大状态机并要求迁移；只从公开列表隐藏会继续在学生本人和直接详情可见；删除全部提醒会破坏已发生通知的历史；允许学生自助删除会改变内部处理与留存责任。因此均不采用。

**后果**：新增 `DELETE /admin/help-requests/{request_id}` 与管理员详情危险操作，现有八个反馈答疑操作增为九个；不新增 Schema、迁移、依赖或 Worker。操作不可由应用恢复，生产使用依赖现有备份制度；应用回滚无需数据库降级，但不会恢复已删除工单。

## ADR-043：账号个人数据物理擦除、共享记录去归属并异步清理对象

**状态**：`Accepted`。

**决策**：真实管理员可永久删除任意非本人账号，用户可从个人资料页注销本人账号。两条路径共用重新认证、邮箱确认、CSRF、管理员生命周期锁、最后管理员保护和脱敏审计；管理员路径另要求内部原因与 PostgreSQL + MinIO 备份确认。用户、Session、令牌及个人业务聚合在单一 PostgreSQL 事务物理删除；平台通知、作业、赛事、问卷、知识库同步运行、团队提交和操作者历史继续保留，用户外键按个人数据 `CASCADE`、共享归属 `SET NULL` 分类。队长在删除前转移，无可转成员时解散队伍，锁定队伍低于最小人数且无豁免时转为失效。

**与既有决策关系**：延续 ADR-004 的服务端 Session、ADR-007 的 PostgreSQL Outbox、ADR-010 的正式版本不可变、ADR-011 的两角色模型和 ADR-013 的优秀作业来源约束。个人提交随账号擦除时，ADR-010 的触发器只在当前事务设置 `pnx.account_erasure=on` 且父提交行已经不存在时允许版本级联 DELETE；普通 UPDATE/DELETE 继续拒绝。历史审计使用既有操作者 `SET NULL` 去标识，但保留目标 UUID 与删除事实。

**原因**：账号主体跨越认证、个人提交、问卷、反馈答疑、赛事成员和文件；继续用“存在引用即拒绝”不能完成真实注销，无差别级联又会删除其他学生依赖的平台或团队记录。PostgreSQL 与 MinIO 没有跨系统事务，因此数据库个人引用必须先原子消失并可靠记录待删对象，再由 Worker 幂等终止 multipart 和删除 MinIO 对象。

**替代方案**：只禁用或软删除不能满足直接清除个人数据；统一 `CASCADE` 会误删共享业务；统一 `SET NULL` 会保留个人回答、工单和提交正文；在 API 事务中同步删除 MinIO 会产生跨系统半完成；按桶扫描回收无法证明引用关系；放宽正式版本触发器的所有 DELETE 会破坏不可变性，因此均不采用。

**安全、备份与降级边界**：成功和拒绝审计不得包含密码、确认邮箱、姓名、学号、对象键、multipart 标识或个人正文；邮件任务清除身份与秘密，安全事件去除用户和邮箱关联。上线 `20260829_0015` 前必须验证新的 PostgreSQL + MinIO 同点加密完整备份。本轮不得读取或测试当前数据库。未执行账号删除且未产生去标识空值时可降级；执行过删除后优先前滚修复，若必须恢复只能把删除前同点备份恢复到隔离环境，不能直接覆盖当前生产库。

**后果**：新增 `DELETE /admin/users/{user_id}` 的高风险请求契约、`DELETE /auth/account`、个人资料注销区、管理员删除确认表单、账号对象清理 Worker 和迁移 `20260829_0015`。Worker 暂停时数据库删除仍提交且对象不再授权，恢复后继续清理；最终失败进入告警。此功能源码完成不等于部署，必须在备份、隔离迁移往返和对象对账通过后才能启用。

## ADR-044：管理员按团队提交引用分层删除队伍

**状态**：`Accepted`。

**决策**：真实管理员可在填写非空内部原因并二次确认后调用 `DELETE /admin/teams/{team_id}`。Service 锁定队伍并统计 `submissions.owner_team_id`：没有历史团队提交时物理删除队伍并依外键级联成员关联；已有历史团队提交时锁定全部当前成员、统一写入离队时间、清空当前队长和当前取消资格元数据、转为 `dissolved`，继续保留队伍壳、成员历史、不可变版本、评语和附件。两种路径都在同一事务写脱敏审计并返回 204；学生入口、常规管理员列表和直接队伍详情随后不可见。

**与既有决策关系**：延续 ADR-005 的 PostgreSQL 约束与事务、ADR-009 的共享提交聚合、ADR-010 的正式版本不可变、ADR-011 的两角色模型和 ADR-023 的新校内赛公告/组队边界。它不改变 ADR-043 的账号擦除编排：删除队伍是管理员对团队聚合的独立高风险操作，不删除用户账号或个人 MinIO 对象，也不放宽历史版本触发器。

**原因**：误建或重复队伍需要从学生与管理员日常视图清理并释放一赛一队占用，但历史兼容赛事可能已经用队伍作为提交所有者。对无提交队伍保留空壳没有价值；对有提交队伍物理删除会破坏共享历史外键和不可变提交链。以真实引用计数决定删除模式能在同一接口下同时满足清理体验与历史完整性。

**替代方案**：始终物理删除会级联或阻断历史团队提交；始终软删除会留下无价值空壳；新增 `deleted_at` 或新状态会扩大模型、查询和迁移面；存在提交时一律拒绝会让错误队伍继续显示；把提交转移到其他队伍会篡改所有者事实。因此均不采用。

**后果**：新增管理员详情危险区、必填原因的 204 DELETE 契约、Repository 引用计数/成员锁和 TEAM-T11～TEAM-T12 回归。复用既有 `dissolved`、`left_at`、外键和审计，不新增 Alembic 迁移或对象清理任务。取消资格队伍进入保留壳时，当前行的取消资格元数据会清除以满足既有状态约束，原事实与原因继续由只追加审计追溯。应用回滚不要求数据库降级，但无法恢复已经物理删除的无提交队伍；源码完成不等于部署。
