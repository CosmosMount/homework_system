# 通知与工作台实施计划

## 问题背景

阶段 2 已完成认证、Session、CSRF、用户基础数据、审计和可靠邮件 Outbox，并在真实 PostgreSQL 与 Compose 中验收。完整首版的下一依赖是阶段 3：让管理员可靠发布通知，让学生只看到自己受众范围内的内容，并用站内未读和工作台形成首个真实业务闭环。

本阶段对应 NEWS-001～NEWS-008、MAIL-001～MAIL-005 的通知邮件部分、FILE-002～FILE-007 的通知附件切片，以及 NFR-002、NFR-005～NFR-006、NFR-008～NFR-009、NFR-011～NFR-012。不得提前实现作业、提交、优秀作业、赛事或队伍业务。

## 需求本质与必要性

- 通知不是公开文章；草稿、定时项、非受众项和归档默认列表必须由后端状态与受众授权共同限制。
- 发布是一个事务性业务动作：状态变化、逐用户站内提醒、邮件 Outbox、审计必须一致，SMTP 故障不能回滚站内发布。
- 全体、届次、方向、并集与交集需要单一受众计算能力；未分类学生只命中全体通知。
- Markdown 必须在服务端转换并清洗，管理预览和学生详情只能使用同一份安全 HTML。
- 通知附件仍必须遵守私有 MinIO、服务端对象键和授权下载；不能为通知另建直传 API 或让应用中转完整文件。
- 工作台当前只展示已落地的通知数据；作业与赛事集合保持真实空数组，后续阶段接入，禁止伪造占位业务数据。

## 现有结构与可复用能力

- 复用阶段 2 的 `AuthenticatedContext`、管理员依赖、CSRF、统一错误、UUIDv7、审计表和请求上下文。
- 复用 `outbox_jobs`、Worker 锁租约、退避、dead 状态、管理查询和人工重试。
- 复用届次、方向与已激活用户查询作为受众计算来源。
- 复用 Next.js 服务端 Cookie 转发、浏览器 API Client、认证后布局和 5000 端口同源部署。
- 复用 PostgreSQL 17 事务、Alembic 命名规范和真实 Compose 迁移往返流程。

## 架构与安全取舍

1. Markdown 使用固定版本的解析器与允许列表清洗器；禁用原始 HTML、远程图片、危险协议、事件属性和内联样式。数据库同时保存原始 Markdown 与清洗后的 HTML，读取不在浏览器重新解释原文。
2. 通知受众配置保存在届次/方向关联表；首次发布时在同一事务内计算激活学生并生成带唯一事件键的 `student_notifications`，形成发布时发送快照。
3. 学生通知内容读取仍按通知受众授权；逐用户站内提醒用于未读与幂等，不替代资源权限。
4. 立即发布在 API 事务内完成；定时发布写唯一 `publish_announcement` Outbox，Worker 到时锁定通知并执行同一发布函数。重复执行只得到一个业务结果。
5. 通知邮件按每个接收者建立唯一 Outbox 任务，只包含标题、摘要和站内链接；不含附件永久地址或其他敏感正文。SMTP 停止不影响发布事务。
6. 为兑现通知附件且保持唯一上传架构，本阶段先实现通用上传模块中仅允许 `announcement_attachment` 的分片初始化、预签名、恢复、完成、终止和授权下载；阶段 4 只扩展作业/赛事上下文与合计规则，不另建路径。
7. 对 PostgreSQL 与 MinIO 的非原子边界继续采用“对象先完成校验、业务事务再绑定、孤立对象延迟清理”；本阶段不实现作业/赛事文件授权。

## 数据库与迁移

新增一条可回滚的阶段 3 Alembic 迁移，创建：

- `announcements`、`announcement_cohorts`、`announcement_directions`；
- `student_notifications`；
- `files`、`upload_sessions`、`upload_parts`、`announcement_files`。

约束包括通知状态与时间一致性、全体受众与分类关联由 Service/事务共同保证、逐用户事件键唯一、对象键唯一、上传状态/分片范围/幂等键、附件不重复绑定和必要外键索引。迁移按外键逆序完整降级，不修改阶段 1～2 表和数据。

## 后端实现

1. 建立统一 Markdown 渲染与清洗模块，覆盖标题以外的用户内容、外链协议、代码块和危险 HTML 语料。
2. 建立 `announcements` 的 ORM、schema、Repository、Service 与 Router；实现管理员列表、草稿创建、读取、按 revision 修改、受众预估、发布/定时、置顶、归档和显式更新提醒。
3. 建立受众计算函数，覆盖全体、单维度、多维并集/交集、停用分类引用和未分类学生。
4. 建立学生通知列表/详情与站内提醒读取、单条已读、范围全部已读；非受众详情统一返回 404。
5. 建立工作台 API，返回当前用户、未读数、最近 5 条可见通知，以及尚未实施业务的真实空集合。
6. 扩展 Worker 调度 `publish_announcement`，复用发布事务并保持任务、站内提醒和邮件幂等。
7. 扩展邮件模板支持通知提醒和更新提醒，继续使用现有退避、脱敏、dead 与人工重试。
8. 实现通知附件所需的通用上传最小切片：服务端对象键、MinIO multipart、分片预签名、完成校验、终止、恢复、授权下载和过期/孤立清理。

## 前端实现

1. 将学生根入口切换为 `/dashboard`，建立学生导航、未读入口和真实工作台；保留 `/app` 为兼容重定向。
2. 新增 `/announcements` 与 `/announcements/[announcementId]`，覆盖搜索、未读筛选、置顶、分页、已读和非受众 404。
3. 新增 `/admin/dashboard` 与管理员通知列表、创建、编辑页面；表单包含 Markdown、受众、接收人数、计划、置顶、邮件和发布确认。
4. 建立安全 HTML 展示组件；不使用 `dangerouslySetInnerHTML` 渲染未经后端清洗的内容。
5. 建立通知附件上传器，复用同源 API 与 MinIO 预签名 URL，显示分片进度、恢复、重试和终止。
6. 增加邮件任务与审计只读管理页面，连接阶段 2 已有管理 API，不暴露 payload 或密文。

## API、权限与部署影响

- 严格实现 `06-api-specification.md` 中 `/dashboard`、`/notifications*`、`/announcements*`、`/admin/announcements*`、`/uploads*` 和 `/files/*/download-url`。
- 所有读取要求有效 Session；管理员写入额外要求 admin 与 CSRF。学生不可见通知统一 404。
- 浏览器上传只通过 Nginx 同源 `/storage` 访问预签名 MinIO 请求；PostgreSQL、MinIO 管理端口和 Worker 不新增主机映射。
- 新增 Markdown/MinIO 客户端依赖必须固定版本并同步锁文件；不引入 Redis、Celery、全局状态库或第二套文件服务。
