# 作业多图片批量上传实施计划

## 背景与目标

现有个人作业版本已经支持 `file_ids` 列表、多个 `version_files` 关联和单版本附件合计上限，学生也可以逐个上传并累加多个附件；实际缺口是浏览器文件选择器与上传状态一次只处理一个文件，选择多张图片时只取第一张。

本任务对应 SUB-001～SUB-004、FILE-001～FILE-007 和 FILE-T01～FILE-T09。目标是在不改变正式版本不可变规则、不新增上传接口且不放宽文件安全策略的前提下，让学生一次选择多张图片或其他作业允许类型的附件，并按选择顺序完成上传后统一加入待提交版本。

## 需求与边界

- 作业上传器允许一次选择多个文件，最多与正式提交接口现有的 100 个附件保持一致。
- 批量文件逐个执行现有完整 SHA-256、multipart、服务端类型检测和完成校验，避免同时散列或上传多个大文件造成浏览器资源峰值。
- 开始上传前校验单文件上限、当前版本剩余总字节和剩余附件数量；任一预检失败时不初始化任何上传会话。
- 批次中已成功文件立即加入待提交附件清单；某个文件失败时保留该文件及后续队列，用户可恢复当前会话并继续，正式版本仍只由用户显式确认创建。
- 通知附件继续保持现有单文件选择行为；通用上传器的批量能力只由作业提交显式开启。
- 不把作业附件限制为图片。可选类型继续由管理员创建作业时冻结的 `allowed_extensions` 与后端全局白名单共同决定。

## 实现范围

1. 扩展 `MultipartUploader` 的可选批量模式，维护待上传文件队列、批次进度、当前恢复会话与终止状态。
2. 作业提交表单开启批量模式，并把已完成附件数量与字节数转换为当前批次可用额度。
3. 补充一次选择两张图片并按序完成的组件测试，以及超出批次剩余总量时不发起上传的测试。
4. 补充提交 Service 多附件顺序与合计上限契约测试，确认后端现有事务路径无需修改。
5. 同步需求、页面、上传、测试、变更记录、当前任务、完成记录和项目基线。

## API、数据库与安全影响

- `POST /uploads/init`、分片预签名、完成接口和正式版本请求结构均不变化。
- `POST /assignments/{assignment_id}/submission-versions` 继续一次接收最多 100 个不重复 `file_id`。
- 数据库 `version_files` 已支持多行及 `display_order`，无需 Alembic 迁移。
- 服务端继续在正式绑定事务中锁定并复核文件所有者、目的、上下文、状态、占用、扩展名与附件合计大小；客户端预检不替代后端校验。
- 文件内容继续只存 MinIO，对象键仍由服务端生成。

## 验证方式

- 前端定向 Vitest：单文件回归、两图片批量上传、总量预检、正式版本表单。
- 后端定向 Pytest：多附件顺序、合计边界与超限拒绝。
- 完整前端 Vitest、ESLint、严格 TypeScript 和 Next.js 生产构建。
- 与风险匹配的后端定向测试、格式/静态检查，以及 `git diff --check`。

## 完成条件

- 文件输入具有批量选择能力，两个合规图片在一次操作中都完成并显示于同一待提交版本清单。
- 批量中断可从失败文件恢复，不重复加入同一已完成 `file_id`，通知上传器行为不变。
- 超出 100 个附件或当前版本剩余字节时，浏览器在初始化上传前明确拒绝；绕过客户端仍由后端拒绝。
- 自动测试与质量门通过，文档明确无 API 形状变化、无数据迁移；本任务未经新的部署指令不构建或替换生产容器。
