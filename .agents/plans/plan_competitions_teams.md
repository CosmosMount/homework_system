# 阶段 5：校内赛、报名、队伍与团队提交实现计划

## 背景与必要性

阶段 1～4 已建立基础设施、认证、通知、个人作业与共享不可变版本链路，并通过真实 Docker Compose 与局域网 `5000` 端口验收。系统下一项核心能力是校内赛闭环：管理员配置赛事和赛题，学生在报名期登记并组队，报名结束后锁定有效队伍，当前队长在提交期代表队伍创建正式版本，当前成员和管理员读取团队版本与私密评语。

本阶段必须复用现有 `submissions`、`submission_versions`、`version_files`、`feedback` 和 MinIO 分片上传能力，避免个人作业与团队赛事形成两套不可变版本实现。同时以数据库约束、事务锁和后端授权共同保证“一赛一队”“只有当前队长提交”“团队评语不外泄”等不可破坏边界。

- 安全与文件：`.agents/docs/08-auth-security-email.md`、`.agents/docs/09-file-upload-storage.md`。
- 页面与测试：`.agents/docs/02-information-architecture.md`、`04-page-specifications.md`、`11-testing-strategy.md`。

## 现有能力与模块职责

- 复用认证上下文、CSRF、统一错误码、审计日志、站内通知、邮件 Outbox 和 Worker。
- 复用共享提交版本、幂等记录、附件绑定、Markdown 清洗和下载授权；扩展所有者维度，不复制版本表。
- 新增 `competitions` 模块承担状态策略、Service 业务规则、Repository 持久化和 Router 协议转换。
- `uploads` 只扩展 `competition_submission` 用途及赛事赛题上下文校验，不让前端接触 MinIO 管理接口。
- 前端沿用 App Shell、通用 API 客户端和 Multipart Uploader，新增学生与管理员赛事工作台。

### 2. 领域模型与状态策略

- 为六个赛事状态实现单向推进：`draft`、`registration_open`、`registration_closed`、`submission_open`、`submission_closed`、`archived`。
- 为队伍实现 `forming`、`dissolved`、`locked`、`invalid`、`disqualified`、`archived`；报名结束时锁定人数有效或获豁免的队伍，其余标记无效。
- 明确时间边界、提前关闭、归档、赛题截止和队伍提交资格，复杂判断放入纯策略函数并覆盖边界测试。
- Worker 幂等推进赛事阶段；在报名结束事务中锁队并校验人数，在提交开始/结束和归档时同步所需状态，不依赖浏览器请求触发。

### 3. 报名、组队与邀请码

- 学生只能在报名期登记或撤回；已有当前队伍时禁止撤回。
- 已登记学生可创建队伍或凭邀请码加入；创建者成为当前队长并写入当前成员记录。
- 邀请码使用安全随机源生成，数据库只存带独立服务端 pepper 的 HMAC，不存明文；创建/轮换时仅在成功响应中返回一次，日志、审计、异常与指标不得包含明文。
- 加入接口按用户/IP 做速率限制，统一处理错误避免邀请码枚举；事务锁与部分唯一索引共同处理并发加入。
- 仅当前队长可轮换邀请码、移除成员、转让队长或在允许条件下解散；成员仅能退出本人，离队前必须先转让队长。

### 4. 团队提交、评语与上传

- 扩展共享提交 Service 和 Repository 支持 `competition_task_id + owner_team_id`，版本号连续、正式版本不可更新或删除、幂等重放语义与个人作业一致。
- 仅 `locked` 且未失效/未取消资格队伍的当前队长能在赛事和赛题有效提交期创建版本；`submitted_by` 记录实际队长。
- 当前团队成员和管理员可以读取该团队全部版本及私密评语；前成员、其他队伍和未授权学生统一返回 404。
- 管理员可对赛事版本创建或修订团队私密评语，通知不含评语正文；赛事版本不能进入优秀作业标记。
- 上传新增 `competition_submission` 用途，校验上传者是当前队长、上下文是目标赛题、文件状态/白名单/总量/未绑定；下载按当前团队成员或管理员授权。

### 5. 管理员纠错与审计

- 管理员可创建/编辑/发布赛事、管理赛题、提前关闭报名或提交并归档。

- 管理接口返回报名、队伍人数、有效性和各赛题提交摘要；所有 revision 更新使用乐观并发控制。

## 风险与控制

- **跨表时间约束**：普通 CHECK 不能引用赛事表；用 Service 校验加数据库触发器或受控事务约束，测试直接 SQL 越界写入。
- **并发组队**：应用预查不足以保证一赛一队；必须保留数据库部分唯一索引，并把冲突映射为稳定 409 错误码。
- **队长成员一致性**：创建队伍需要先后写队伍与成员；使用可延迟约束触发器，在事务结束验证，不制造不可提交的中间状态。
- **邀请码泄漏**：明文只存在于请求处理内存和一次响应，禁止进入审计 change summary、日志与数据库；pepper 通过环境变量提供并验证强度。
- **提交所有者混淆**：共享表使用数据库二选一约束，Repository 查询显式区分个人/团队，所有优秀标记再次拒绝赛事版本。
- **历史成员隐私**：读取权限按 `left_at IS NULL` 的当前成员判断，不因曾经加入而永久获得访问权。

## 完成标准

## 2026-08-29 管理员删除队伍修订

### 背景与必要性

现有管理员只能补录、移除成员、转让队长、豁免人数或取消资格，无法清理误建、重复或不再应展示的队伍。单纯从前端隐藏不能释放一赛一队约束；直接物理删除所有队伍又会破坏历史赛事团队提交、不可变版本、评语和附件的所有者引用。因此本次在既有队伍生命周期内增加真实管理员删除入口，并按是否存在历史团队提交选择可追溯的删除模式。

### 删除语义与影响

1. 新增 `TEAM-009` 与 `DELETE /admin/teams/{team_id}`；请求必须携带非空管理员原因，成功返回 `204 No Content`。
2. Service 先锁定队伍。队伍没有任何 `submissions.owner_team_id` 引用时，物理删除队伍并依赖纯关联外键级联删除成员轨迹；已有历史团队提交时不得物理删除，而是把全部当前成员写入 `left_at`、清空当前队长、转为 `dissolved` 并保留队伍壳、成员历史、提交、版本、评语和附件。
3. 已有提交的取消资格队伍转为 `dissolved` 时清除队伍行上的当前取消资格元数据，以满足既有状态约束；原取消资格事实与原因继续由既有只追加审计保留。删除审计只记录目标 UUID、原状态、删除模式、释放人数、历史提交数量和管理员原因，不记录成员身份、邀请码、提交正文、附件名或对象键。
4. 物理删除和保留壳两种模式都立即释放当前成员的一赛一队占用；学生“我的队伍”、公开目录和直接队伍入口随后不可见。常规管理员赛事统计、队伍列表与队伍详情排除 `dissolved`，历史提交仍可由真实管理员按既有兼容权限读取。
5. 前端队伍详情增加独立危险区，要求复用管理员原因并进行明确二次确认；成功后用 `router.replace('/admin/competitions')` 离开已删除详情，失败时保留页面和统一 API 错误。
6. 本修订复用现有 `dissolved` 状态、外键和审计表，不新增字段、枚举、依赖或 Alembic 迁移；应用回滚不要求数据库降级，但不会恢复已经物理删除的无提交队伍。
