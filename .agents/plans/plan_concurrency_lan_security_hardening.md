# 高并发、局域网入口安全与 Docker 版本收敛计划

## 背景与必要性

既有隔离诊断已经证明 Backend 与 PostgreSQL 能完整处理 100 个有效账号的同时登录；同一来源 IP 经 Nginx 仅 21 个成功、其余 79 个被 `auth_limit` 拒绝，拒绝没有进入 Backend。用户明确要求保留单 IP 大量账号的限制，因此该行为属于安全防护而不是并发缺陷，但 Nginx 默认返回 503 会把限流误报成服务故障，应修正为标准 429。

本轮还需要用多个独立 Docker 来源 IP 提高登录及登录后读取强度，验证连接池、Session 完整性、延迟与错误率；并只针对本机、本项目的局域网入口检查常见攻击面和前端敏感实现泄漏。最后收敛 PNX 项目的旧镜像版本，避免长期堆积，同时保留当前运行版本与至多一个明确回滚版本。

## 目标与范围

1. 保留按真实来源 IP 的认证粗限流与应用层失败登录限流，将 Nginx 超限状态规范为 429，并补充开发、生产配置契约测试。
2. 在隔离 Compose 项目中准备 300 个虚构学生，以多个独立负载容器模拟不同来源 IP，执行 100、200、300 账号登录突发及更高强度的登录后典型读取；统计 HTTP 状态、网络错误、P50/P95/P99、吞吐、Session 数量和服务健康。
3. 仅针对本机暴露的 PNX 入口验证端口边界、匿名授权、Host/转发头伪造、Origin/CORS/CSRF、非法方法、请求体上限、路径遍历编码、安全响应头、服务版本、source map、内部地址和秘密泄漏；不扫描或攻击局域网其他主机。
4. 盘点所有 PNX 容器、镜像、卷和网络；删除本轮隔离资源、无容器引用的旧 PNX 应用镜像及 dangling 构建层，仅保留当前运行镜像和至多一个可识别回滚版本，不删除运行数据卷、数据库备份或现有服务。
5. 更新测试、容量、安全、部署、运维、变更、任务和阶段记忆，并按“入口修复与测试契约”“运行验证与运维记录”分 commit 提交。

## 实施约束

- AUTH-009 仍要求按规范化账号和来源 IP 限制失败登录；不得为了压测通过而取消或信任客户端伪造的 `X-Forwarded-For`。
- 生产只允许 Nginx 暴露 80/443（容器映射为受控的 8080/8443）；Backend、Frontend、PostgreSQL、MinIO 管理端口不得直接暴露。
- 负载数据和密码只存在临时隔离环境，密码文件必须为绝对路径且权限 0600；不连接真实 SMTP、飞书或现有运行数据库。
- Web 前端不能从根本上阻止合法客户端逆向；本轮验收目标是没有 source map、秘密、内部凭证、MinIO 对象键、管理端口或不必要版本信息泄漏，并维持服务端鉴权。
- 发现持续 5xx、服务不健康、连接池耗尽或资源显著失控时停止加压并保留诊断证据；不以单 IP 429 计入真实并发错误。
- Docker 清理前先解析运行中镜像与候选回滚镜像，精确删除；保留既有未跟踪文件 `infra/compose/Dockerfile.knowledge-hotfix.backend`。

## 验证方式

- 配置与静态质量门：Nginx `-t`、开发/生产 Compose 解析、后端定向 Pytest、Ruff、格式检查和严格 Mypy；若源码范围扩大，再运行完整后端质量门。
- 多来源登录：100、200、300 个有效账号，各来源不超过粗限流突发；成功率目标 100%，不得出现 5xx、网络错误或半写入 Session。
- 登录后读取：至少 100 个独立 Session，逐级提高到资源允许的更高强度；正式 NFR-T03 场景要求非上传 API P95 < 500 ms、错误率 < 1%。
- 局域网安全：只探测已确认属于本机 PNX 的监听地址和入口，验证安全头、授权边界、输入边界及静态产物泄漏；仓库和镜像秘密/漏洞扫描优先复用 `infra/security/scan.sh`，外部漏洞库不可用时如实标记。
- 清理后验收：现有六个 Compose 服务保持 healthy，四个健康端点返回 200，运行镜像仍有明确标签，数据卷与备份保留，`docker image ls` 不再存在多余 PNX 历史版本。
