# 唯一账号管理员保证与服务重建计划

## 状态

已完成（2026-08-25）。

## 背景与必要性

当前空库首个完成邮箱验证的账号会成为管理员，但历史数据库若在该规则上线前已经存在唯一的 `active student`，不会自动修正，导致系统明明只有一个可用账号却没有管理入口。仅在前端把该账号“视为管理员”会绕过后端授权和审计，因此必须把角色持久化为真实 `admin`。

## 目标与范围

- 系统只有一个账号、且该账号已完成邮箱验证并处于 `active` 时，必须保证其角色为 `admin`。
- 保留空库首个完成验证账号的并发安全授予；不提升 `pending_email` 或 `disabled` 账号，不增加第三种角色。
- 登录事务使用既有固定 PostgreSQL advisory lock 检查其他账号；需要提升时写审计、撤销旧 Session，再创建管理员 Session。
- 新增可前滚的数据迁移，部署时立即修正当前唯一的历史 `active student`；降级不自动撤销已经授予的管理员角色，避免系统重新失去管理员。
- 重建 Backend/Worker 和 Frontend 镜像，运行迁移并替换服务，最后通过 `5000` 端口验收。

## 影响

- Backend auth/users Repository 与 Service、登录 Router、认证与迁移测试。
- Alembic head、认证/安全/API/数据库/测试/部署/决策/变更记录。
- Frontend 无新增业务实现，但需要重新构建以确保上一任务的管理员页面进入运行镜像。

## 验证

- 先补唯一 active student 登录后成为管理员的失败回归，并确认多账号、待验证、禁用和既有管理员行为不变。
- 运行完整后端 Pytest、Ruff、格式和严格 Mypy；运行前端 Vitest、ESLint、严格 TypeScript 与生产构建。
- 验证迁移链单一 head，升级后当前唯一账号为 admin 且存在脱敏审计；复验六个运行组件与管理员页面/API。

## 数据与回滚

- 不新增或删除表、列、索引；迁移只在“用户表恰好一行、该行 active + 已验证 + student”时修正角色并追加审计。
- 应用镜像可回滚；数据降级保留已授予的 admin，后续如需角色调整必须通过受审计的管理员接口，不能由迁移静默降级。

## 完成结果

- Backend 完整 130 项测试、Ruff、136 个 Python 文件格式检查和 100 个应用源文件严格 Mypy 通过；Frontend 36 项测试、ESLint、严格 TypeScript 和生产构建通过。
- `20260825_0007` 已应用到开发 Compose；Backend、Worker、Frontend 和 Nginx 使用新镜像或配置重建，六个常驻服务全部健康，`5000` 端口页面与 API 路由验收通过。
- 部署时数据库实际有 21 个用户行（5 个 `admin`、16 个 `student`），不满足唯一账号条件，因此迁移按设计没有改变角色、撤销 Session 或写授予审计；未删除任何历史账号。
