# SMTP 验证邮件受控恢复计划

## 状态

已完成（2026-08-25）。

## 背景与问题本质

部署方已把最新 SMTP 参数写入 `.env`，但当前 Worker 容器仍使用创建时注入的旧环境：SMTP 主机为示例占位，用户名和密码为空。因此 Outbox 会持续按退避策略重试，修改宿主机环境文件本身不会让已运行容器自动加载新配置。

此前重发页面的成功空响应缺陷导致用户在误以为请求失败后多次重试。近期数据库中存在 7 个验证邮件任务，其中 6 个对应的一次性令牌已经被后续重发失效，只有 1 个令牌仍有效。直接让旧任务全部经新 SMTP 投递会发送多封无效链接，违反 AUTH-002、MAIL-004～MAIL-005 和用户“不乱发邮件”的明确要求。

## 需求与影响

- 对应 AUTH-002、AUTH-005、MAIL-001～MAIL-005、NFR-008、NFR-012。
- 不改变公开 API、页面行为、Outbox 状态枚举或数据库结构。
- Worker 在发送邮箱验证/密码重置邮件前复核事件关联的一次性令牌；已使用、已过期、用途不匹配或已被替代的令牌不得连接 SMTP。
- 失效令牌任务使用现有 `dead` 状态和稳定错误码 `TOKEN_SUPERSEDED` 终止，保留历史与脱敏摘要，不删除任务或密文。

## 实现步骤

1. 先增加 Worker 回归测试，证明失效令牌邮件不会调用邮件发送器，仍有效的令牌只发送一次。
2. 在 Repository 增加按令牌 ID 读取能力；Outbox Service 负责解析事件键、复核令牌用途/有效期并把失效任务安全终止。
3. 运行 Ruff、格式、严格 Mypy、定向及完整后端测试。
4. 使用不执行 `MAIL FROM/RCPT/DATA` 的 SMTP 连接、STARTTLS 与认证预检，确认配置和凭证可用但不发送邮件。
5. 构建 Backend 镜像；停止旧 Worker 后，全量脱敏复核未完成任务，将失效任务与唯一最新有效验证任务调度为立即处理，再用新镜像和新环境重建 Worker；其他历史有效任务保持退避时间。
6. 观察 Outbox：失效任务进入 `dead/TOKEN_SUPERSEDED`，唯一有效任务至多发送一次；复验 Worker 心跳、六服务健康和局域网 `5000`。
7. 同步安全、测试、变更记录、项目记忆和任务台账。

## 安全与回滚

- SMTP 预检只建立连接、STARTTLS 和认证后退出，不提交发件人、收件人或正文。
- Worker 停止后才调整 `available_at`，避免旧代码与新 SMTP 配置并发投递；失效任务必须通过令牌表联接筛选，有效任务只允许选择按创建时间排序的最新一条。
- 若 SMTP 预检失败，不重建 Worker、不调整队列，并报告不含凭证和完整服务响应的错误分类。
- 若新 Worker 异常，停止 Worker 并回退到原镜像；Outbox 记录保留，`dead/TOKEN_SUPERSEDED` 任务本就不可投递，无需恢复。
- 不输出邮箱、SMTP 主机、用户名、密码、令牌、Cookie 或密文载荷。

## 完成标准

- 最新 SMTP 配置由运行中的 Worker 正确加载。
- 失效的一次性令牌邮件不会调用 SMTP，唯一有效验证邮件最多投递一次。
- 相关质量门、容器健康、Worker 心跳和脱敏 Outbox 状态验证通过。
- 明确记录实际投递数量、失败风险和本次不涉及数据库迁移。

## 实际结果

- 通知定向 8 项测试、Ruff、127 个 Python 文件格式、100 源文件严格 Mypy 和完整 127 项后端测试全部通过。
- SMTP 连接、EHLO、STARTTLS、认证与 QUIT 预检成功，未执行 `MAIL FROM`、`RCPT TO` 或 `DATA`。
- 停止旧 Worker 后确认 3 条有效邮箱验证任务和 15 条失效验证/重置任务；只调度其中最新有效任务，另外 2 条保持原退避时间且重试均晚于令牌过期时间。
- 新 Worker 加载最新 SMTP 环境并健康运行；本次窗口实际发送 1 条邮箱验证任务，15 条失效任务全部进入 `dead/TOKEN_SUPERSEDED`，剩余失效任务为 0。
- Backend、Frontend、PostgreSQL、MinIO、Nginx、Worker 六个常驻服务健康；Nginx 和 API 就绪经 `5000` 返回 200，Frontend 根路径按预期返回 307。
- 未调用重发/重置 API、未创建额外邮件任务、未输出任何邮箱或秘密；不涉及数据库迁移。
