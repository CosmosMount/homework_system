# 当前工作树分提交与高并发压力测试计划

## 背景与必要性

当前工作树同时包含账号活跃度/安全清理、多题实名问卷，以及管理员用户页按钮与状态展示修复。两项主体功能分别引入 `20260827_0012` 和 `20260828_0013`，迁移链存在先后依赖；若不先核对差异、质量门和迁移 head 就直接一次性提交，后续审查、回滚和部署定位都会困难。

用户同时要求尝试高并发压力测试。项目 NFR-003 与 NFR-T03 已规定 300 个激活账号、100 个并发浏览会话、非上传 API P95 小于 500 ms且错误率低于 1%；仓库已有秘密安全的 `infra/performance/read_load.py`，应优先复用并只针对隔离容量数据执行，避免污染当前真实开发账号和业务数据。

## 目标与提交边界

1. 先检查全部未提交差异、未跟踪文件、迁移链和测试状态，修复会阻止质量门或造成明显运行错误的当前改动，不做无关重构。
2. 按可独立审查和回滚的主题提交：
   - 账号活跃度、十天提醒与受保护账号清理；
   - 多题实名问卷及 `0013` 兼容迁移；
   - 管理员用户操作按钮与中文状态/搜索 UI；
   - 权威文档、任务记录与本次验证记录在对应实现提交中同步，避免孤立文档漂移。
3. 临时隔离构建文件、运行秘密、密码文件、压测报告原始敏感上下文和容量数据不进入 Git；无法证明属于产品源码的未跟踪文件不提交。
4. 提交完成后保持工作树干净；若存在必须保留但不应提交的现场文件，明确列为遗留项。

## 验证方式

- 静态与单元质量门：后端 Ruff、格式检查、严格 Mypy、完整 Pytest；前端 ESLint、严格 TypeScript、完整 Vitest 和 Next.js 生产构建。
- 迁移：确认 Alembic 单一 head，覆盖 `0011 → 0012 → 0011 → 0012` 与 `0012 → 0013 → 0012 → 0013` 的真实 PostgreSQL 往返；若环境权限不允许，则保留已通过的离线 DDL 结果并明确阻塞，不把静态生成等同于真实迁移验收。
- 运行态：检查 Compose 服务与 Nginx/API 健康端点；压力测试前后再次检查健康与近期严重错误。
- 高并发读取：在隔离容量项目、300 个虚构学生和受控 0600 密码文件可用时，运行 100 个独立 Session、5 轮、共 2,000 次典型读取，请求验收为总体 P95 < 500 ms、错误率 < 1%。
- 可选上传并发：只有隔离 MinIO 容量环境、足够磁盘空间和明确测试账号可用时，才运行 20 路 multipart；不得对当前业务数据或真实账号执行容量写入。

## 风险与安全边界

- `0013` 依赖 `0012`；拆分提交必须保持任一提交点的 Alembic 单一 head 和可导入源码，不得制造悬空 revision。
- 账号永久删除不可由应用回滚，本任务只验证规则和测试，不对现有账号调用删除接口。
- 高并发测试可能消耗 CPU、数据库连接和对象存储空间；使用已有工具的固定上限与超时，执行前后记录健康状态，发现错误率持续上升、服务不健康或资源耗尽即停止。
- 若只能访问当前非隔离运行环境，则最多做无写入的短时健康/匿名并发探测，并把它标记为尝试结果，不冒充 NFR-T03 正式容量验收。
