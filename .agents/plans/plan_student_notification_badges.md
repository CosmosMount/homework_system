# 学生提醒分类与徽标消除修复计划

## 背景与问题本质

当前学生侧栏把 `student_notifications` 的全部未读数量集中显示在“通知”入口。管理员处理反馈答疑、作业延期或私密评语后产生的提醒也会抬高该数字，但学生进入公告列表时只能看到未归档公告，因而会出现“侧栏有未读、公告列表却为空”的矛盾状态。公告归档后，既有未读记录仍然参与聚合；反馈答疑详情也没有复用公告详情的显式已读动作。

本任务对应 `NEWS-003`、`NEWS-005`、`HELP-002`、`HELP-005` 与既有站内提醒契约。目标是让徽标落在提醒实际指向的业务入口，并让已读或已失效的提醒从相应徽标中消失，不引入新的通知中心、角色、依赖或数据库迁移。

## 产品规则

- “通知”徽标只统计未读的公告发布与公告更新提醒；已归档公告不再计数。
- “反馈答疑”徽标只统计本人未读的答疑解决/修订提醒；管理员学生视图按本人账号使用同一规则。
- 已有作业延期和私密评语提醒归入“作业”入口，避免继续错误占用公告徽标；历史赛事私密评语按目标 URL 归入校内赛入口。
- 工作台保留全部有效站内提醒总数，同时返回公告、作业、校内赛和反馈答疑的分类未读数；分类之和与有效总数一致。
- 公告归档事务同时把该公告现存未读提醒标为已读；查询侧也排除历史遗留的已归档公告未读记录，保证部署后无需数据迁移即可消除旧徽标。
- 公告和本人工单详情继续使用显式 POST 已读接口；打开页面不会通过 GET 隐式写数据库。反馈答疑详情只暴露当前用户可操作的未读提醒 ID，不返回事件键、答复正文到通知或其他用户数据。

## 影响范围

### 后端

- 扩展 `StudentNotificationRepository`：按目标业务域统计有效未读数、查询本人指定目标的未读提醒 ID，并在公告归档事务中锁定和消除对应未读提醒。
- 扩展工作台响应，保留 `unread_count` 并新增结构化分类计数。
- 扩展本人工单详情响应，返回该工单当前未读解决提醒 ID；管理员响应不增加该字段。
- 不改变提醒创建的幂等事件键、反馈答疑答复事务、邮件 Outbox 或资源授权。

### 前端

- `AppShell` 接收分类未读数，在通知、作业、校内赛和反馈答疑入口分别显示徽标及无障碍文案。
- 所有学生页面从工作台响应传入同一分类计数，管理视图保持无徽标。
- 反馈答疑详情增加与公告一致的“将相关提醒标为已读”操作，成功后刷新服务端权威状态。
- 工作台公告区域只使用公告分类未读数，避免把答疑/作业提醒链接到空公告筛选页。

### 文档与数据

- 同步产品需求、信息架构、页面、API、数据库说明、测试策略、变更记录、项目基线和任务记录。
- 本次只改变查询和状态更新语义，不新增字段、表、索引或 Alembic 迁移；已有归档公告未读记录通过查询过滤自然失效，新归档记录在同一事务标为已读。

## 实施步骤

1. 先补充分类统计、归档消除和目标提醒 ID 的后端测试，再实现 Repository、Service 与 Schema。
2. 扩展前端类型和共享侧栏，批量接入所有学生页面，并为反馈答疑详情增加显式已读操作。
3. 增加侧栏分类徽标、答疑已读按钮与工作台公告计数的前端回归。
4. 更新权威文档和任务记录，复查既有“已解答问题公开”未完成工作不被覆盖。
5. 运行后端定向测试、Ruff/格式/严格 Mypy，以及前端定向测试、ESLint、严格 TypeScript 和生产构建；根据环境与风险决定是否执行完整测试，不部署、不迁移现有运行库。

## 验收标准

- 只有答疑解决提醒时，“通知”无徽标而“反馈答疑”显示正确数量；只有公告提醒时行为相反。
- 作业与历史赛事提醒显示在各自入口，不再混入公告。
- 公告归档后相应徽标立即消失，历史遗留归档提醒也不计入；单条标记已读后相应分类和总数减少。
- 本人工单解决/修订后出现答疑徽标，详情可把该工单相关提醒标为已读，其他工单提醒不被误清除。
- 匿名、越权、管理员学生视图和现有公告/答疑隐私边界保持不变。
- 无数据库迁移、无新依赖、无站内通知正文泄露。
