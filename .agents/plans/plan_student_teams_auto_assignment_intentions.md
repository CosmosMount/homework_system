# 学生校内赛组队与意向调查计划

## 背景

学生赛事入口目前仍按“赛事列表”组织，单一校内赛产品约束下需要直接成为队伍中心；同时平台缺少用于收集学生方向/参与意向的调查能力和移动端填写入口。

2026-08-28 运行态回归发现管理员创建带选项的调查时返回 500：父调查和选项同时进入 SQLAlchemy Session，但 ORM 未建立可保证插入顺序的关系依赖，实际先插入选项并触发 `intention_options.survey_id` 外键失败。本计划继续作为该意向调查域的唯一正式计划，追加最小持久化顺序修复，不新建重复计划。

2026-08-28 用户进一步要求把单题“意向调查”升级为多题问卷：管理员可设置“第一志愿、第二志愿”等多个单选/多选题，查看实名提交名单，并限制每名学生的提交次数。本计划继续作为该领域唯一正式计划，追加问卷升级，不创建第二份计划。

2026-08-28 用户继续要求问卷生成后可以查看并修改且直接部署。本轮沿用该唯一正式计划：新增任意状态管理详情，开放草稿的完整编辑；已开放且可能存在答案的题目结构保持只读，避免历史选择失去含义。实现后执行完整质量门、数据库备份、固定镜像部署和数据不变性验收，不新增迁移、不触发飞书同步。

2026-08-30 用户要求已关闭问卷允许重新开启。本轮继续沿用该领域唯一正式计划：在不开放题目结构编辑、不重置历史回答或累计提交次数的前提下，允许真实管理员执行 `closed → open`；归档仍为终态，重新开启后原开始/结束时间窗口与提交上限继续生效。本轮不新增字段或迁移。

2026-08-30 用户要求问卷支持邮件通知，并确认由管理员手动选择成员发送。本轮继续沿用该领域唯一正式计划：问卷开放后，真实管理员通过既有管理员用户搜索加载激活学生，逐个选择成员并显式发送；服务端重新校验所选账号仍为激活学生，邮件 Outbox 与脱敏审计在同一事务提交，SMTP 故障不影响问卷及回答。

2026-08-30 用户进一步要求可以按技术组选择或向全部成员发送。本轮在原手动成员模式上新增 `direction` 与 `all` 范围：前端从统一方向 API 加载激活技术组，后端按发送瞬间解析对应激活学生，不由浏览器分页枚举 UUID；停用/不存在技术组、空范围均拒绝。三种范围继续共用开放窗口、成员事件键去重、Outbox、脱敏审计和安全邮件模板，无数据库迁移。

2026-09-03 用户要求把现有意愿选择问卷中所有人的第一志愿直接配置为技术方向。本轮继续沿用该领域唯一正式计划：真实管理员在问卷卡片中读取按题序排列的第一道单选题，为它的每个选项显式映射一个启用中的技术方向并二次确认；服务端锁定问卷，以事务开始时的最新回答为准，批量覆盖当前已验证激活学生的 `direction_id`。未提交者、非激活账号和非学生账号不变，操作不修改问卷答案，也不重算已发布作业的固定受众快照。本轮复用既有用户方向字段和审计表，无数据库迁移或新依赖。

2026-09-04 用户要求管理员用户管理界面可以按技术组查看人员，并让问卷邮件通知支持多选技术组。本轮继续沿用本计划：用户页复用既有 `GET /admin/users?direction_id=` 服务端过滤，把技术组写入 URL 并在搜索、活跃度、分页和写后刷新间保留；问卷 `direction` 邮件范围改为选择 1～100 个不重复激活技术组，服务端在事务内整体校验并按这些组的并集合并当前激活学生。为支持 Backend/Frontend 分阶段替换，后端暂时兼容旧单个 `direction_id` 输入，但新前端和正式契约使用 `direction_ids`。两项能力均复用现有方向、用户和 Outbox 数据，不新增迁移或依赖。

2026-09-04 用户进一步要求问卷支持分技术组填写。本轮仍沿用本计划：问卷草稿显式选择“全部学生”或 1～50 个不重复启用技术组，只有当前方向命中目标组的学生才能在开放窗口内从列表、详情、二维码和提交接口访问；前端隐藏不能替代 Service/Repository 鉴权。受众在首次开放后随问卷内容一起冻结，关闭后重新开启沿用原受众；既有问卷迁移后默认面向全部学生。统计分母和邮件“全部”范围按当前目标激活学生计算，手动或技术组邮件不得包含问卷目标外成员，避免发送无法填写的链接。


## 目标与决策

- 学生 `/competitions` 只展示当前未归档校内赛公告摘要、我的队伍状态和可加入队伍目录；队伍目录支持名称搜索，只返回仍在成形且未满的公开摘要。
- 保留现有邀请码加入流程，并增加“没有队伍？自动分配”：仅报名期、已报名且无队伍的学生可以主动申请；事务锁住赛事和候选队伍，优先加入人数较少的成形队伍，没有可用队伍时创建系统生成队伍，继续由一赛一队唯一索引兜底并写审计。
- 新增独立意向调查域：管理员创建调查和单选/多选选项，开放/关闭调查；学生登录后填写或修改自己的回答；管理员只看到汇总人数和比例，不向学生公开他人回答。
- 管理员可生成调查填写二维码。二维码定位地址使用不可猜测的调查 token，但填写页仍要求登录，token 只定位调查，不作为身份凭证；不新增匿名改答流程。
- 用户界面统一使用“问卷”；已有 `/intentions` 路由、数据库表前缀和内部模块名继续作为兼容标识，避免破坏历史二维码与链接。
- 一份问卷包含 1～30 个必答选择题，每题独立配置单选或多选及 1～30 个选项；“第一志愿”“第二志愿”等是独立题目，不把优先级编码进选项或固定用户字段。
- 问卷受众只能为全部学生，或 1～50 个不重复启用技术组的并集；未设置技术组的学生只能填写全部学生问卷。受众只允许在 `draft` 创建或修改，首次开放、关闭、重新开启和归档均保留该配置；学生方向变化会影响后续读取与写入资格，但不会删除既有回答。
- 问卷可配置每人最多提交次数，留空表示不限；每次成功保存当前答案消耗一次，达到上限后服务端拒绝再次提交。管理员名单展示提交人姓名、学号、邮箱、最新答案、累计提交次数和最后提交时间，不向学生公开他人答案。
- 已有单题调查迁移为只含一个问题的问卷，原选项和回答关系保持不变；原回答修订次数初始化为已提交次数，已有调查默认不限次数，避免升级后阻止原有改答流程。
- 管理员可读取任意状态问卷的 Markdown 源说明、时间窗口、提交限制和完整题目/选项；仅 `draft` 可携带 revision 原子替换内容，开放、关闭或归档问卷只读。
- 已关闭问卷可由真实管理员重新开启，随后也可再次关闭；重新开启不修改题目、选项、二维码 token、历史最新答案、累计提交次数、原时间窗口或提交上限。已归档问卷不可重新开启。
- 问卷开放后，真实管理员可按姓名、学号或学校邮箱搜索激活学生并手动选择 1～100 名成员发送填写提醒；前端不得传入任意邮箱，后端只按用户 UUID 重新校验 `role=student AND status=active` 后读取其已验证学校邮箱。
- 同一接口同时支持按多个激活技术组和问卷全部目标学生发送；技术组/全部范围只由服务端查询发送时的权威成员集合，不受管理用户分页影响，也不接受前端提交展开后的邮箱或 UUID 列表。一个学生只有一个当前技术组，多个组按并集解析，成员级事件键继续保证范围重叠时不重复入队；手动成员和技术组范围必须整体落在问卷受众内。
- 请求范围必须互斥：`manual` 只带 1～100 个不重复成员 UUID，`direction` 只带 1～100 个不重复技术组 UUID，`all` 不带成员或技术组；任一技术组不存在/停用或最终收件人数为 0 时整体拒绝。旧单个 `direction_id` 只作为滚动发布兼容输入，不能与 `direction_ids` 同时提交。
- 管理员用户页复用既有单个 `direction_id` 服务端筛选，可选择全部技术组或任一现有技术组查看人员；技术组、搜索、活跃度与页码共同写入 URL，筛选变化回到第一页，分页、清除搜索、越界页规范化和账号写后刷新继续保留技术组。
- 同一问卷每次开放周期以问卷当前 revision 和学生 UUID 形成唯一事件键；同一成员重复选择只报告已入队，不重复发送，问卷关闭再重新开启后可在新 revision 下再次手动通知。
- 邮件只包含收件人称呼、问卷标题和站内 `/intentions/{survey_id}` 填写链接，不包含问卷答案、补充说明、二维码 token、管理员信息或永久资源地址；管理员邮件页继续只返回掩码收件人和安全任务元数据。
- 第一志愿方向配置只接受问卷按 `display_order` 排序后的第一题，且该题必须为单选；请求必须覆盖该题全部选项，并把每个选项显式映射到一个当前启用的技术方向，防止按标签猜测或遗漏选项。
- 第一志愿方向配置只对标题去除首尾空白后精确等于“意向选择”的问卷开放；其他标题、附加前后缀或近似文案不显示入口，直接调用 API 也在读取题目或写入任何方向/审计前整体拒绝。
- 批量操作只处理仍为 `active student` 的最新回答者，并覆盖其已有方向；相同方向计为未变化，未提交者及已禁用、待验证或管理员回答者计为跳过且不写入。服务端按稳定顺序锁定目标用户并在同一事务更新 `direction_id`、`revision`、逐用户脱敏方向调整审计和问卷级汇总审计。
- 管理端必须在提交前说明覆盖范围并二次确认；成功结果显示符合条件、实际更新、方向未变化和跳过数量。操作可安全重复执行，但它是显式快照应用而非持续同步；开放问卷后续改答不会自动改方向，管理员需要再次主动执行。
- 批量方向配置不修改问卷、回答、提交次数或二维码，不撤销 Session，也不补写或重算既有 `assignment_audience_users`；后续新发布内容按用户新方向匹配，之后首次激活学生仍沿用既有开放作业补录规则。

## 2026-08-28 创建故障修订结果
