# 成功空响应兼容修复计划

## 状态

已完成（2026-08-25）。

## 背景与问题本质

重发验证邮件与密码重置申请按 API 契约统一返回 `202 Accepted`，且响应体为空。前端统一 API Client 当前只把 `204 No Content` 识别为无正文，其他成功状态一律调用 `response.json()`，导致重发验证页面把已经被服务端接受的请求错误显示为 `Unexpected end of JSON input`。

本次对应 AUTH-002、AUTH-005、AUTH-009 与 `06-api-specification.md` 的两个 `202` 认证端点。问题位于通用前端响应解析边界，不改变后端、SMTP、Outbox、接口路径或返回状态。

## 现有能力与影响范围

- 复用 `frontend/lib/api/client.ts` 的统一成功/错误响应处理，不在认证表单增加端点特判。
- 复用 `frontend/tests/api-client.test.ts` 的 Fetch 模拟能力，构造内存中的 `202` 空响应进行回归测试。
- `EmailRequestForm` 已使用 `apiFetch<void>`，修复统一客户端后，重发验证和密码重置申请会共同恢复正确的成功提示。
- 不调用真实重发接口，不触发 Worker 或 SMTP，不创建新的 Outbox 邮件任务。

## 实现步骤

1. 先增加 `202` 成功空响应的前端回归测试，确认现有实现可复现解析异常。
2. 调整统一 API Client：成功响应先读取文本，空白正文返回 `undefined`，非空正文继续解析 JSON；错误响应保持原有统一错误结构。
3. 运行定向测试、完整前端测试、ESLint、严格 TypeScript 与生产构建。
4. 更新测试策略、变更记录和任务台账；本次不涉及数据库迁移。
5. 仅重建 Frontend 并复验服务健康和局域网 `5000` 页面，不发送真实邮件。

## 风险与控制

- **误吞异常正文**：只对 `response.ok` 且正文为空白时返回 `undefined`；非空正文仍必须是合法 JSON，否则保留解析失败，避免隐藏协议错误。
- **错误结构退化**：非 2xx 响应继续走现有 `parseError`，不改变请求 ID、字段错误和限流信息。
- **误发邮件**：测试只模拟浏览器 `Response`，运行态验收不提交重发或重置表单，也不调用相应 API。

## 完成标准

- `202` 空响应不再触发 JSON 解析异常，并返回 `undefined`。
- 现有 JSON 成功响应、`204` 空响应及统一错误解析保持通过。
- 前端质量门、生产构建、容器健康和局域网 `5000` 页面通过。
- 文档明确记录验证过程中没有发送测试邮件，且无数据库迁移。

## 完成结果

- 统一 API Client 对成功响应先读取文本；空白正文返回 `undefined`，非空正文继续解析 JSON，错误响应路径保持不变。
- 新增 `202` 空响应回归测试，旧实现稳定复现原始异常，修复后定向测试和完整 32 项前端测试通过。
- ESLint、严格 TypeScript、主机及容器 Next.js 生产构建全部通过。
- 仅替换 Frontend 容器，Backend 与 Worker 未重启；六服务健康，本机和局域网 `5000` 页面均为 200。
- 全部验证使用模拟响应或页面 GET，没有调用重发/重置 API，没有创建或发送测试邮件；本次无数据库迁移。
