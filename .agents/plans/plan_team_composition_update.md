# 队伍方向配额调整计划

## 背景与必要性

当前 TEAM-004 的规则为机械 2 人、嵌入式控制/硬件合计 1～2 人、算法 1 人。现要求改为机械 1～2 人、嵌入式控制 1 人、嵌入式硬件 1 人、算法 1 人，完整队伍共 4～5 人；原规则会错误允许两个控制或两个硬件占满共享名额，并将机械仅 1 人的队伍标为未齐全。

## 范围与影响

- 后端统一方向分类、组队上限与完整性判断；现有建队、邀请码加入、邀请、申请审批、自动分配、管理员补录、自助与管理改方向、方向改名继续复用这一判断。
- 控制方向识别“嵌入式控制”“嵌入式-控制”，硬件方向识别“嵌入式硬件”“嵌入式-硬件”“硬件”，均允许“组”后缀；笼统“嵌入式”和合并名称不推断具体岗位。
- 更新队伍详情的方向分布字段和学生/管理员页面文案；保留既有队伍与成员，不自动改组。
- 原始 `teams.max_members` 继续作为兼容容量；前端呈现和 API 返回的有效容量最多为 5 人，低于 5 的已有容量仍生效。不改变表结构或历史队伍记录。
- 影响 TEAM-004～TEAM-006、TEAM-008、TEAM-011、TEAM-016、AUTH-014、INT-008；接口契约变化先核对 `06-api-specification.md`，数据设计核对 `07-database-schema.md`。

## 实施与验证

1. 修改共享配额逻辑与响应字段，统一有效容量的展示，更新前端类型和两处队伍分布展示。
2. 覆盖机械 1/2 人的完整状态、控制与硬件各 1 人上限、未知方向拒绝、已有超配队伍的展示及加入/改方向路径。
3. 运行相关后端测试、前端测试与静态检查，核对 API schema 与差异。更新需求、页面、API、数据库说明、测试策略、决策和变更记录。
4. 更新任务记录；源码阶段不执行生产部署或数据写入。后续部署按下方用户授权的追加流程执行。

## 回滚与迁移

无数据库结构或数据迁移；回滚应用恢复旧校验和响应契约。旧队伍不会被自动拆分，新规则下不合规的既有队伍需通过成员退出或方向调整人工修正。
