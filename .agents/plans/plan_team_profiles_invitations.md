# 校内赛个人简介与邀请组队计划

## 背景与必要性

当前“校内赛”已经是全局独立队伍中心，学生可以创建队伍、输入一次性邀请码加入或主动自动分配，但公开目录不展示人员，成员只能在拿到邀请码后被动加入。新需求需要增加自愿公开的组队个人简介，让学生先了解其他学生的方向与自述，再通过站内邀请完成组队；队长不是永久身份，成队后仍可在当前成员间变更。

本任务继续遵守 TEAM-001～TEAM-009 的独立队伍边界，不恢复赛事实体、报名、赛事作品或团队提交。新增 TEAM-010～TEAM-013，个人简介和站内邀请只服务于组队。

## 产品与安全决策

- 个人简介使用独立的 `team_profiles`，由 active student 自愿创建和修改；未提交简介的账号不进入简介目录。简介正文为 1～2,000 字符纯文本，前端按纯文本换行展示，不接收或渲染 HTML。
- 简介目录只对有效角色为 student 的登录态开放，分页返回提交者姓名、技术方向和简介；不返回邮箱、学号、Session、队伍邀请码或其他私密资料。本人简介可在同一页面编辑。
- 已属于未满 `forming` 队伍的任一当前成员都可从他人简介发出站内队伍邀请；目标必须是另一名已提交简介的 active student，且当前没有队伍。邀请固定关联发送时的队伍，不暴露邀请码。
- 邀请状态为 `pending/accepted/declined/cancelled`。同一队伍对同一受邀者最多一条 pending 邀请；重复发送幂等返回现有邀请。受邀者只能处理发给本人的 pending 邀请。
- 接受邀请时锁定邀请、队伍与当前成员关系，重新校验邀请仍有效、队伍未满、受邀者未加入其他队伍；成功后加入队伍并把本人其余 pending 邀请标为 cancelled。拒绝只改变邀请状态。
- 邀请发送者后续离队不使邀请泄露或自动换队；只要关联队伍仍为 forming 且未满，邀请仍可由受邀者接受。队伍解散或管理员物理删除时邀请分别取消或级联删除。
- 创建队伍的学生初始成为队长；当前队长可以在任意两名当前成员之间转让，管理员纠错能力保留。前端在我的队伍中明确展示和操作该能力。
- 简介保存、邀请发送/接受/拒绝和队长转让均要求后端有效角色、同源与 CSRF；关键写入使用脱敏审计，不记录简介正文、姓名、学号、邮箱或邀请码。

## 数据迁移

新增接在 `20260904_0020` 后的 `20260907_0021`：

1. 新建 `team_profiles`：`user_id` 主键及 `introduction`、`created_at`、`updated_at`、`revision`；用户删除级联删除简介。
2. 新建 `team_invitations`：邀请、队伍、受邀者、发送者、状态和处理时间；队伍/用户删除级联，状态和时间使用检查约束。
3. 为受邀者状态查询和队伍状态查询建立索引；用 partial unique index 保证同队同目标最多一条 pending 邀请。
4. downgrade 先删除邀请再删除简介；旧队伍、legacy 赛事与文件对象不受影响。生产迁移前必须完成 PostgreSQL 与 MinIO 同点可恢复备份。

## 后端改造

- 扩展 teams ORM 与 Repository，封装简介分页、本人简介 upsert、邀请列表、加锁读取、状态变更和取消逻辑。
- Service 负责 active student、简介可见性、当前成员、目标资格、队伍容量、一人一队、邀请状态、并发冲突与脱敏审计；Router 只处理协议转换。
- 新增 `GET /team-profiles`、`GET/PUT /team-profiles/me`、`GET/POST /team-invitations`、`POST /team-invitations/{id}/accept`、`POST /team-invitations/{id}/decline`。
- 队伍解散、成员通过邀请加入和账号删除路径补齐邀请状态/级联语义，不连接 legacy 赛事提交。

## 前端改造

- 新增 `/competitions/profiles` 组队个人简介页面，包含本人简介编辑、简介目录、搜索分页、邀请按钮和本人收到的待处理邀请。
- `/competitions` 增加“浏览个人简介与邀请”入口；本人队伍成员卡片显示方向/简介可用状态，并继续提供清晰的队长转让操作。
- 新增 API 类型与 Server Component 读取封装；写操作使用既有 `csrfFetch`，成功后刷新 Server Component 数据。
- 移动端保证简介阅读、邀请、接受/拒绝和队长转让可用，交互具备明确 loading、成功与错误状态。

## 文档与追溯

- 同步项目总览、产品需求、信息架构、页面、架构、API、数据库、安全、测试、路线图、变更记录、项目基线与任务记录。
- 集中追溯矩阵扩展为 TEAM-001～TEAM-013，新增 TEAM-T13～TEAM-T18。

## 验证方式

- 后端定向测试：简介可见性/字段最小化、upsert revision、任一成员邀请、目标资格、重复邀请、接受/拒绝、容量、一人一队、并发冲突、邀请取消、权限/CSRF 与审计脱敏。
- 前端定向测试：个人简介编辑、目录邀请、待处理邀请、无队伍/满队/本人按钮状态、接受后刷新和队长转让。
- 迁移测试：head 更新、离线 SQL、隔离 PostgreSQL `0020 → 0021 → 0020 → 0021`，检查索引、级联与模型漂移。
- 完整质量门：Pytest、Ruff、格式、严格 Mypy；Vitest、ESLint、严格 TypeScript、Next.js 生产构建；OpenAPI、`git diff --check` 与赛事残留边界扫描。

## 回滚与风险

- 应用回滚到旧版本前应先停止新邀请写入；旧应用会忽略新表，但数据仍保留。需要数据库回滚时，`0021 → 0020` 会删除全部简介和邀请，必须先备份或导出。
- 邀请属于瞬时组队状态，不发送邮件、不包含邀请码，也不自动加入；并发接受以数据库当前成员唯一索引和 Service 锁为最终边界。
- 本任务只实现源码、迁移、测试和权威文档，不连接或修改当前运行 PostgreSQL/MinIO，不构建镜像、不部署。
